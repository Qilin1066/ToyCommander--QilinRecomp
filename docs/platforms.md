# Where players can play: desktop, Raspberry Pi, Android, iPhone and iPad

The game's code may never be distributed (it is made from the disc), so on every system the player's own disc is recompiled and the result compiled for their device. The question per system is where that compile happens and how the result gets onto the device. Researched 2026-11-28; sources at the end. Claims not confirmed in a primary source are marked *(unconfirmed)*.

## Desktop: Windows, Linux, macOS (the launcher)

One launcher program (`tools/player-kit/launcher`), the same logic everywhere; the system's parts are `platform_*.cpp`, `process_*.cpp`, `shortcut_*.cpp`. It names no game: the game's names, its data (a disc image or a folder), how that is identified (`identify`, the recompiler's JSON answer), the recompiler's steps, what a compile needs and how the game starts are all `kit/game.txt`'s, so the same folder is copied unchanged into the sister projects (`launcher/ADOPTING.md`: the keys, the identify contract, what a project provides, and `LAUNCHER_VERSION`). Each download carries or finds a compiler:

| System | Download | Compiler | Notes |
|---|---|---|---|
| Windows 10/11 x64 | zip, `Play <Title>.exe` | LLVM-MinGW, bundled | unsigned: SmartScreen's "More info, Run anyway" once |
| Linux x86-64 and ARM64 | `.tar.gz`, `Play <Title>` | zig (MIT), bundled: its own libc++, the system's glibc (2.35 or later) | menu entry from the launcher; needs a Vulkan 1.3 driver |
| macOS 14.5+ (Xcode 16's tools need it; the runtime itself is built for 10.15), Apple silicon and Intel | `.dmg`, `<Title>.app` (universal) | Apple's clang from the Command Line Tools (free; Apple's SDK may not be redistributed): the launcher offers Apple's installer | MoltenVK (Apache-2.0) inside the app; unsigned: "Open Anyway" in Privacy & Security once (notarisation needs a paid Apple developer account) |

### The macOS download

`tools/player-kit/package-macos.sh` (CI: `.github/workflows/player-kit-macos.yml`) builds one universal disk image, `<Package>-X.Y.Z-macos.dmg`: `<Title>.app`, a link to `/Applications` and `README.txt` (from `README-macos.txt.in`).

- **The app.** `Contents/MacOS/Play <Title>` (the launcher), `Contents/Frameworks/libMoltenVK.dylib` (MoltenVK's own release, pinned by SHA-256), `Contents/Resources/AppIcon.icns` (`launcher/make_icns.py`, the `.ico`'s artwork), `Contents/Resources/LICENSES` and `Contents/Resources/kit`: `qilin`, `lib/lib<game>_kit.a` (both universal; the archive merged by Apple's `libtool`, `tools/player-kit/macos.cmake`), `include/`, `build-flags.txt`, `game.txt` (`compiler=/usr/bin/clang++`), `files.txt` (paths relative to the app, the iOS kit's files too) and `VERSION`; and `Contents/Resources/ios-kit`, the iOS kit for "Play on iPad" (below, under the iPad). The build's `work/` is in `~/Library/Application Support/qilin/<game>`, so the app is never written to and its seal stays whole.
- **Flags.** `build-flags.txt` names each processor's own flags beside the shared ones (`native.arm64 = -arch arm64 -mcpu=native`, `native.x86_64 = -arch x86_64 -march=native`, `ldflags.<arch>`): the launcher takes the Mac's own architecture (`host_architecture()`, Apple silicon even under Rosetta), so the game is built for that Mac only. `$kit` becomes the kit's whole path there (work/ isn't beside it).
- **Apple's compiler.** Before a build, `launcher/apple_tools.cpp` runs `xcode-select -p` and `clang++ --version`: missing tools get "Install Apple's command line tools" (`xcode-select --install`, Apple's own dialog) and "Check again"; an unagreed licence says so; Apple clang older than 16 says to update macOS's software.
- **MoltenVK.** volk opens `libvulkan.dylib`, `libvulkan.1.dylib`, then `libMoltenVK.dylib` by name, and SDL3, given no library, takes any `vkGetInstanceProcAddr` already in the process, which in the game is volk's variable. So the launcher starts the game with `DYLD_FALLBACK_LIBRARY_PATH` set to the app's `Frameworks` alone (volk finds the app's MoltenVK, and not a Vulkan SDK's loader) and `SDL_VULKAN_LIBRARY` set to the same file. The launcher's own window needs neither: SDL looks in `@executable_path/../Frameworks` first, and falls back to its software renderer.
- **Gatekeeper.** Signed ad hoc after assembly (`codesign -s -`: the dylib and `qilin`, then the app); nothing removes quarantine. The README and the release notes give the one-time "Open Anyway" steps.
- **CI's checks.** `tools/player-kit/check-macos.sh` mounts the image on an Apple silicon and an Intel runner: the layout, `lipo` (universal), `codesign --verify --deep --strict`, `files.txt` against the app, then a stand-in game compiled and linked with the kit's flags by `/usr/bin/clang++` and started (it must load and print its usage).

### Linux

`tools/player-kit/package-linux.sh` builds it, `.github/workflows/player-kit-linux.yml` on every push and a game's tag, each processor on its own runner (`ubuntu-22.04`, `ubuntu-22.04-arm`): `<Package>-X.Y.Z-linux-x86_64.tar.gz` and `-linux-arm64.tar.gz`, the folder `<Package>/` with `Play <Title>`, `README.txt` (`README-linux.txt.in`), `LICENSES/` and `kit/` (as `kit.hpp` lists, with `icon.png` for the menu entry and zig in `toolchain/zig`).

- **zig** 0.17.1, pinned by its SHA-256 in the workflow, the whole release less other systems' C libraries and headers (Windows, macOS, the BSDs, WebAssembly; about 130 MB of 300). `game.txt` says `compiler=toolchain/zig/zig`, `compiler_args=c++`.
- **The kit is built with the same zig** (`zig cc`/`zig c++` as CMake's compilers, through wrapper scripts the package script writes), so the archive's libc++ is the one the player's link uses. The target is the native one (zig finds the system's X11, Wayland and sound headers for SDL3 and links against the glibc it finds), with `-mcpu=baseline` so nothing is compiled for the runner's own processor; the player's compiles add `build-flags.txt`'s `native` line (`-march=native` on x86-64, `-mcpu=native` on ARM64).
- **glibc 2.35 is the floor**: the runner's (Ubuntu 22.04). The download runs on Ubuntu 22.04, Debian 12, Fedora 36, Raspberry Pi OS Bookworm and later. An older glibc target (`-target <arch>-linux-gnu.2.31`) would drop the native include paths SDL3 needs, so it wasn't tried. The smoke test fails any program in the download that needs a newer glibc symbol.
- SDL3 builds its Wayland support with zig once its own protocol headers come before the system's (`CMakeLists.txt`: zig searches `/usr/include` before SDL's system folder).
- **Checks in CI**: the launcher's tests built with the bundled zig, and `tools/player-kit/smoke-linux.sh` on the unpacked tarball: the layout and `files.txt`, the bundled zig compiling, linking and running a C++23 program with `build-flags.txt`'s flags, the kit's library linked into a game program with an empty function table (not run), the recompiler reading a stand-in boot file, and each program's glibc symbols and libraries. The launcher's window, the menu entry and the update can't be run there.
- zig keeps its compiled libc++ and C runtime in `~/.cache/zig`: the first link on a player's computer builds them for its processor, which adds to the first build's time (most on a Pi).

## Raspberry Pi

The Linux ARM64 download, built on the Pi itself.

- **Graphics.** The game needs Vulkan 1.3. Mesa's v3dv driver reached 1.3 on both the Pi 4 and the Pi 5 in Mesa 24.3. The current Raspberry Pi OS (Trixie, October 2025) ships Mesa 25.0, so it is fine. Bookworm's Mesa is older (Vulkan 1.2 *(unconfirmed)*): the launcher checks the driver's version before building (`launcher/vulkan_check.cpp`: a minimal instance through volk) and, if it's too old, says to update Raspberry Pi OS (a Pi is known by its device tree's model). Where there is a graphics processor, Mesa's software device (llvmpipe, which has 1.3 and may be installed beside an older v3dv) doesn't count; with no graphics processor at all (a virtual machine), it does.
- **64-bit only.** The 64-bit OS has been the default download since October 2023; 32-bit images are about a sixth of 64-bit downloads. On a 32-bit system the launcher (a 64-bit program) can't start, so the download's README and the release notes say "64-bit Raspberry Pi OS" first (the README with "`getconf LONG_BIT` says 64"). There is no start script to say it at start-up: a shell script is opened in a text editor or behind a "run or display?" question when double-clicked in GNOME's Files and Raspberry Pi OS's file manager, where the program itself just runs; and the launcher's menu entry, update and folder lock find the download through its own path, which a wrapper would move to another name. On a 32-bit OS with a 64-bit kernel (the 32-bit image boots one on a Pi 4 or 5 *(unconfirmed)*) the system's message is "No such file or directory" (no 64-bit loader), which the README names too.
- **Memory.** Pis have 1 to 16 GB. The launcher runs no more compilers at once than free memory allows (game.txt's `compile_memory_mb`: 1.2 GB each here): a 2 GB Pi compiles one file at a time, an 8 GB Pi four. A 1 GB Pi is below what the build needs.
- **Time.** The first build is CPU-bound: tens of minutes on a Pi 4 *(to be measured)*, much less on a Pi 5. Later builds take compiled files from the cache. The progress bar says it may take a while on a Raspberry Pi.
- **Space.** The 2 GB check applies; an SD card is slower but the compile is CPU-bound.
- **Desktop.** Raspberry Pi OS runs Wayland (labwc). Whether a file chooser exists there (a GTK portal or zenity) is unconfirmed, so the launcher accepts a dragged file and, where there's no dialog, a typed or pasted path. "Add to the applications menu" puts it in the Pi's menu.

Next steps: on a real Pi, measure a first build on a Pi 4 (4 GB) and a Pi 5 (with zig's own first libc++ build), the peak memory of the largest generated file and the start-up's hashing of the kit (the 170 MB zig program is hashed into the build's identity at every start), then tune the per-compiler allowance; and confirm the Vulkan check's messages, the file chooser and the menu entry on labwc.

## Android: not pursued

The owner, 2026-11-28: "Forget android, those users can sort installation out themselves". No Android build or installer is made here. What was found, for whoever takes it up: an app can't compile and run code on the device (Android 10's execute restrictions); the workable route is a computer building the APK (a fixed template plus the player's native library, signed with a local key) and installing it over adb, which is exempt from Google's coming developer verification. Vulkan 1.3 only (the owner's decision) leaves out the NVIDIA Shield TV (Vulkan 1.1) and Fire TV sticks (Vega OS, or Vulkan 1.1 at best); recent tablets have 1.3. The renderer uses only two 1.3 features (dynamic rendering, synchronization2), in a few places, should a 1.1 path ever be wanted.

## iPad (and iPhone)

The owner, 2026-11-28: the iPad is wanted.

**On the device: impossible.** App Review guideline 2.5.2 forbids apps executing code that changes their features, and iOS doesn't let apps run generated code.

**The route: a Mac, from the Mac download's own app.** Its launcher gets "Play on iPad":

1. **Checks.** Full Xcode (the Command Line Tools have no iOS SDK: `xcrun --sdk iphoneos --show-sdk-path`), an Apple ID signed in to Xcode (its development team, from the signing certificates or Xcode's settings), and an iPad connected and trusted, with Developer Mode on (`xcrun devicectl list devices`). Each missing piece gets a plain message and what to do (App Store link for Xcode; Xcode, Settings, Accounts; the iPad's Settings, Privacy & Security, Developer Mode).
2. **Build.** The disc's recompiled code is the same C++ as for the Mac (`work/gen`): the launcher compiles it for iPadOS (`xcrun --sdk iphoneos clang++ -target arm64-apple-ios…`) with its usual pool and a cache of its own, into one static library. The iOS kit (in the app's `Contents/Resources/ios-kit`) holds the runtime built for iPadOS (static, with SDL3 and MoltenVK), `build-flags.txt`, and a small Xcode project that links the two. `xcodebuild -allowProvisioningUpdates` builds and signs it with the player's team and a bundle identifier made once per player.
3. **Install.** `xcrun devicectl device install app`, then the disc image copied into the app's Documents (`devicectl device copy to`): a `.chd` is one file, which is easiest; a `.cue` goes with its tracks.
4. **Seven days.** With a free Apple ID the app stops opening after 7 days. The launcher shows when, and "Reinstall on iPad" signs and installs again without rebuilding. A paid developer account ($99 a year) makes it a year. Free accounts: at most 3 such apps on a device (both games count).

**The Mac launcher's side** (`launcher/ios_install.cpp`, macOS only; the parsing in `launcher/ios_text.hpp`, tested by `launcher_test ios`). "Play on iPad" is on the Ready screen when the app has `Contents/Resources/ios-kit/build-flags.txt`. It opens a panel of three checks, looked at again with "Check again" (and the device every few seconds while it isn't ready):

- *Xcode:* `xcrun --sdk iphoneos --show-sdk-path`. None: "Install Xcode from the App Store" (`macappstores://`, Xcode's page). An Xcode in `/Applications` that isn't the selected developer folder is used anyway, through `DEVELOPER_DIR` on every Apple tool the launcher runs, and the player is told the `sudo xcode-select -s` line. Then `xcodebuild -license check`, `xcodebuild -checkFirstLaunchStatus` ("Open Xcode" once) and `xcrun --find devicectl` (Xcode 15 or newer).
- *The team:* Xcode's accounts (`defaults export com.apple.dt.Xcode`, as XML: any dictionary with `teamID`, `teamName`, `isFreeProvisioningTeam`) and the keychain's development identities (`security find-identity -v -p codesigning`), whose certificates (`security find-certificate -a -p -c <name>`) give the team in the subject's OU: the identifier in the common name's brackets is the person's, not the team's. None: "Xcode > Settings > Accounts, add your Apple ID". Several: the player chooses; the choice is kept in `ios-team.txt` in the data folder.
- *The device:* `xcrun devicectl list devices --json-output`: physical iOS devices only, each with what's missing (connected by cable or on the same network, Trust, Developer Mode in Settings > Privacy & Security, the restart). Several: the player chooses (`ios-device.txt`).

"Build and install" compiles `work/gen` for iOS with the Mac build's pool (`compile_lifted` in `build.cpp`) and its own cache (`build-cache-ios`; the key starts with the target and the SDK's path), into `work/ios/obj`, archives it with `xcrun libtool -static` into `work/ios/libqilin_lifted.a`, copies the kit's Xcode project to `work/ios` (xcodebuild writes beside a project, and the app is sealed), and runs `xcodebuild -allowProvisioningUpdates -allowProvisioningDeviceRegistration` for the chosen device (`-destination platform=iOS,id=<udid>`) with `DEVELOPMENT_TEAM`, `PRODUCT_BUNDLE_IDENTIFIER` (`io.github.qilinrecomp.<game>.r<8 hex>`, made once per player: `ios-bundle-id.txt`), the two libraries' settings and `QILIN_IOS_KIT` (the kit's folder in the app). Then `devicectl device install app`, and the disc's files (the image, and a `.cue`'s FILE lines or a `.gdi`'s tracks) copied into Documents with `devicectl device copy to`, each one skipped when `devicectl device info files` lists it with the same size. The profile's dates (`security cms -D -i embedded.mobileprovision`) say until when it works: a profile of 8 days or less is a free team's, shown as "Works on <device> until <date>". "Reinstall on iPad" runs xcodebuild and the install again, without compiling or copying. The last install is kept in `ios-install.txt`; everything is logged to `work/ios/build.log` (the checks to `checks.log`).

The iOS kit's parts are named in its `build-flags.txt`, with these defaults: `kit_lib = lib/lib<game>_ios_kit.a`, `xcode_project = xcode/QilinGame.xcodeproj`, `xcode_scheme = QilinGame`, `xcode_configuration = Release`, `lifted_lib_setting = QILIN_LIFTED_LIB`, `kit_lib_setting = QILIN_KIT_LIB`; `cxxflags` (with `$kit`) compiles the lifted code (`-arch arm64` is added if it names no target). What only a real Mac with Xcode and an iPad can confirm: the layout of Xcode's account settings, devicectl's JSON (the device states, and the answer of `device info files`, which Apple doesn't document), whether a free team signs from the command line with `-allowProvisioningDeviceRegistration`, and the wording of the failures the launcher turns into plain messages.

**The game on iPadOS** (the runtime port, done: below): SDL3 for iOS (UIKit) and MoltenVK linked in statically; the disc found in Documents; saves and settings in Documents, so the Files app and backups see them; the game paused when the app goes to the background and resumed after; controllers through SDL (Xbox, PlayStation and MFi pads all work on iPadOS): controller first. Touch controls on screen come second.

### The iOS kit: the contract with the Mac app

The Mac download's app carries it as `Contents/Resources/ios-kit/` (`tools/player-kit/package-ios-kit.sh <game> <version> <out> device`, called by `package-macos.sh` or given to it built as `IOS_KIT`). The launcher's "Play on iPad" builds the iPad app from it; nothing in it is made from the game. Its `README-ios.txt` states the same settings for the launcher.

| Path | What |
|---|---|
| `lib/lib<game>_ios_kit.a` | One static archive, arm64 devices (`iphoneos` SDK), iOS 16 or newer: everything but the lifted code (the game's library and the runtime, SDL3, Dear ImGui, volk, libchdr with LZMA, miniz, zstd's decompressor and dr_flac, and MoltenVK). Merged by Apple's `libtool` (`tools/player-kit/ios.cmake`). |
| `include/` | The runtime's headers (`recomp/runtime/*.hpp`), as the desktop kit's `include/`. |
| `build-flags.txt` | `name = value` lines, `$kit` the ios-kit folder: `sdk = iphoneos` and `cxxflags = -target arm64-apple-ios16.0 -O2 -DNDEBUG -std=c++23 -w -ffp-contract=off -I$kit/include`. No `native` line: the code runs on every arm64 iPad and iPhone the iOS version runs on. |
| `xcode/` | `QilinGame.xcodeproj` (one target and a shared scheme, both `QilinGame`), `Info.plist`, `Game.xcconfig` (this game's defaults), `QilinGame.xcconfig` (the build settings), `app.c` (Xcode links a target only with a source of its own), `Assets.xcassets` (the icon: `launcher/make_icon.py`'s artwork as one opaque 1024-pixel square, `tools/player-kit/ios/make_ios_icon.py`). |
| `README-ios.txt`, `VERSION` | The settings below; the release. |

The build, as `README-ios.txt` gives it:

1. Each lifted `.cpp`: `xcrun --sdk iphoneos clang++ <cxxflags> -c <file>.cpp -o <file>.o`; then one archive, `xcrun --sdk iphoneos libtool -static -o <work>/liblifted.a <the .o files>`.
2. `xcode/` copied to a folder the launcher can write (the app's copy is sealed and read-only), then
   `xcodebuild -project <work>/xcode/QilinGame.xcodeproj -scheme QilinGame -configuration Release -destination generic/platform=iOS -derivedDataPath <work>/derived -allowProvisioningUpdates DEVELOPMENT_TEAM=<team> PRODUCT_BUNDLE_IDENTIFIER=<id> PRODUCT_NAME=<Exe> QILIN_LIFTED_LIB=<work>/liblifted.a QILIN_KIT_LIB=$kit/lib/lib<game>_ios_kit.a QILIN_IOS_KIT=$kit build` (the launcher also passes `CODE_SIGN_STYLE=Automatic`, `-allowProvisioningDeviceRegistration` and `-destination platform=iOS,id=<udid>`). The project reaches into the kit only through `QILIN_IOS_KIT` (its default, the folder above the project, holds only for the kit's own copy); everything else it needs is inside `xcode/`, so the launcher's copy in `work/ios/xcode` builds as the kit's own would (CI's check builds such a copy). The names the launcher reads from `build-flags.txt` if present (`kit_lib`, `xcode_project`, `xcode_scheme`, `xcode_configuration`, `lifted_lib_setting`, `kit_lib_setting`) are all its defaults here, so the kit sets none of them.
   The app is `<work>/derived/Build/Products/Release-iphoneos/<PRODUCT_NAME>.app`. `build` is the documented action (enough for a development install); `archive` works too. Paths may contain spaces (CI's check builds in a folder with one). Optional: `QILIN_DISPLAY_NAME` (under the icon and in the Files app; default the game's title), `MARKETING_VERSION`, `CURRENT_PROJECT_VERSION` (default the kit's version). The project links `-ObjC "$(QILIN_LIFTED_LIB)" "$(QILIN_KIT_LIB)" -lc++ -liconv` and the frameworks SDL3 and MoltenVK need (UIKit, Foundation, QuartzCore, Metal, IOSurface, CoreGraphics, CoreVideo, CoreMedia, CoreAudio, AudioToolbox, AVFoundation, CoreMotion, GameController, CoreHaptics weakly).
3. Install with `devicectl device install app`, and copy the disc image into the app's `Documents/` (`devicectl device copy to`, the app's data container).

**iOS 16** is the minimum, as planned: nothing found needs another (the runtime's C++ library features need iOS 13; MoltenVK and SDL3 support older). Whether iPads before the A12 have what the renderer needs through MoltenVK is unconfirmed.

**MoltenVK** is the same release as the macOS download's (v1.4.2): its `MoltenVK-ios.tar`, pinned by SHA-256 in the workflow, the static library from `MoltenVK.xcframework/ios-arm64`, unchanged. MoltenVK's release builds use no private API (the private-API build is a separate macOS-only download, `MoltenVK-macos-privateapi.tar`), so it is the App Store–compatible one. Its licences (and SPIRV-Cross's, SPIRV-Tools', SPIRV-Headers', cereal's) are the macOS download's `LICENSES/MoltenVK`, whose `ABOUT.txt` names the iOS library too. CI's Simulator check takes the Simulator's library from `MoltenVK-all.tar` (pinned too), which the download doesn't carry.

### The game on iPadOS

The same runtime with `QILIN_IOS` (CMake: `-DCMAKE_SYSTEM_NAME=iOS`, `-DCMAKE_OSX_SYSROOT=iphoneos` or `iphonesimulator`, arm64; only the kit's target is built there: `<game>_ios_kit`).

- **Start-up.** SDL3's own `main` (`SDL_main.h`, included by `shinobi/src/main.cpp` on iOS) starts UIKit and calls the game's `main` on the main thread, which then owns the loop as on a desktop: SDL's events pump UIKit's run loop. iOS gives the main thread a 1 MB stack, too small for lifted code (Windows' game gets 16 MB), so the game runs on a 16 MB stack of its own on the same thread (`host/src/ios.cpp`, `run_on_big_stack`: a few instructions of assembly switch the stack pointer and back; the frame-pointer chain runs on through, and nothing is thrown across it). Guest threads already have 16 MB pthreads on Apple systems.
- **Vulkan.** MoltenVK is linked in (iOS apps can't load a library of their own), and its library defines every Vulkan function under its own name, which volk's pointers share: on iOS volk is compiled as C++ with `VOLK_NAMESPACE` (its pointers in namespace `volk`) and given MoltenVK's `vkGetInstanceProcAddr` with `volkInitializeCustom` (`host/src/moltenvk.cpp`, a file that doesn't include volk). The window is a Metal one, and its surface is made from SDL's Metal view's layer with `VK_EXT_metal_surface`: SDL's own Vulkan loading is never used, so its search for `vkGetInstanceProcAddr` can't find volk's (the trap the macOS download met).
- **The disc.** No command line: the one disc image in the app's `Documents` (`.chd`, `.cue` or `.gdi`, by `Disc::is_image`; names starting with a dot, such as the Mac's `._` files, are skipped), where the Mac app copies it and the Files app shows it. None, or more than one: a plain message saying what to do (the Mac app's "Play on iPad", or the Files app: On My iPad, the game) with "Check again" and "Quit". A document picker ("Choose a disc") isn't there yet: a `.cue` needs its tracks beside it, so a picker would have to take several files at once.
- **Storage.** `Documents/qilin/<game>` is the data folder (`host/src/paths.cpp`): with `UIFileSharingEnabled` and `LSSupportsOpeningDocumentsInPlace` the Files app shows Documents, so players can see and copy saves and add texture packs, and backups include it. `log.txt` there is the last start's log (nobody sees an app's stderr; `QILIN_LOG=console` in the launch environment keeps it on stderr). Fatal errors are shown in a message before the app ends.
- **Lifecycle.** From SDL's "will enter background" (the app no longer in front: the home screen, Control Centre, a call) the display draws nothing and waits for the GPU's work to finish (iOS allows no GPU work in the background), and at the next vertical blank the game parks (`dreamcast/src/video.cpp`, `park_in_background`): its time stopped and its sound device paused, nothing extra saved. On "did enter foreground" it goes on, and the swapchain is made again at the next present. While the settings menu is open the menu keeps its own pause.
- **Input.** Controllers through SDL's gamepad API as on the desktops (MFi, Xbox and PlayStation pads, through Apple's GameController framework; SDL's HIDAPI is off on iOS, so no Bluetooth permission is needed). Back and Start together open the settings, as everywhere (a keyboard's F1 or Esc too). A touch is SDL's mouse: it works the menu like a click and does nothing harmful in the game. Touch controls on screen are later work.
- **Display.** The whole screen, landscape only, the status bar hidden (`UIStatusBarHidden`, and SDL's full-screen window), the home indicator hidden with the screen's edges kept for the game first (SDL's `SDL_HINT_IOS_HIDE_HOME_INDICATOR` "2"). The picture is widened for the screen as on the desktops; the settings menu, the hint and the frame times keep to SDL's safe area (the rounded corners, the home indicator's strip). The menu's window and refresh-rate settings are hidden there. "Restore and restart" in the menu closes the app (it can't start itself again); the restore happens at the next start.
- **Not changed:** the guest's 4 GB address-space reservation. Recent iPads should allow it without the extended virtual addressing entitlement *(unconfirmed)*; if one refuses, start-up says "cannot reserve 4 GB of address space", and that entitlement is the fix.

### CI

`.github/workflows/player-kit-macos.yml`, job `ios-kit` (each game, `macos-15`): MoltenVK's iOS and all-platforms releases fetched and checked; the kit built for a device and for the Simulator; then `tools/player-kit/check-ios-kit.sh`: each kit's layout and archive (arm64 only, MoltenVK and `main` in it), `link_check.cpp` (an empty function table) compiled with `build-flags.txt` and archived as the lifted library, and the app built by the kit's Xcode project, unsigned (`CODE_SIGNING_ALLOWED=NO`), for a device and for the Simulator, from a copy of `xcode/` in a folder with a space in its name, with `QILIN_IOS_KIT` given as the launcher gives it; the app's program, `Info.plist` and icon checked. The Simulator's app is installed on an iPad Simulator and started with `QILIN_IOS_SELFTEST=1`: it must log the no-disc message, make MoltenVK's Vulkan device in the Simulator, present frames and end. It logs to its `log.txt` like a player's start, which the check reads from the Simulator's app container (a console attached by `simctl launch --console` was found to end before the app did); a fatal signal or `exit()` in the self test logs a backtrace. The Simulator's Metal (GPU family Apple 2, argument buffers tier 1) aborts in MoltenVK's argument-buffer descriptors at the first `vkUpdateDescriptorSets`, so in the Simulator only `host/src/ios.cpp` sets `MVK_CONFIG_USE_METAL_ARGUMENT_BUFFERS=0`; devices keep MoltenVK's default. The `package` job puts the device kit into the app (`IOS_KIT`), and `check-macos.sh` checks it there and in `files.txt`.

**What only a real iPad can show:** signing with a player's team and installing; the game running (a disc, the renderer on an Apple GPU through MoltenVK, sound, the memory card), controllers, the background and foreground cycle, the safe area and home indicator, the 4 GB reservation, and the big stack under UIKit with real use.

Windows and Linux players: no sanctioned route. Compiling for iOS needs Apple's iOS SDK, which comes only with Xcode on a Mac; AltStore and SideStore only re-sign an app someone has built. The EU's alternative marketplaces, web distribution and TestFlight all mean distributing the built game, which is the one thing this project can't do.

## Order of work

1. Linux and macOS downloads (released in Toy Commander 0.15.0, Toy Racer 0.8.0), then the Raspberry Pi measurements and a first run on a real Mac.
2. iPad: the runtime port and the iOS kit (CI: device build and Simulator), then the Mac launcher's "Play on iPad"; then a first install on the owner's iPad; then touch controls.
