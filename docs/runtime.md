# The runtime and the bring-up

What runs the lifted program: guest memory, the registry of native replacements, the start-up, and the stops that say what to write next. The game's program is `toycommander` (it was `qilin_run` during the early bring-up: `docs/naming.md`).

## Building and running
The program is built only from the player's own boot file, as Punch-Out's is from its `main.dol`:

```sh
build/qilin extract path/to/game.cue --out extracted        # outside the repo, or in an ignored folder
cmake -S . -B build -DQILIN_TOYCOMMANDER_BOOT=extracted/files/1GUTH.BIN   # or the disc's .cue
cmake --build build --target toycommander
build/toycommander path/to/game.cue
```

`toycommander` opens a window (SDL3, Vulkan 1.3: the sister projects' host layer, `host/`) and shows each scene the game renders. Variables for the bring-up: `QILIN_HEADLESS=1` draws without a window (machines without a display, and the tests); `QILIN_SCALE=<n>` sets the host pixels per game pixel (default 2); `QILIN_SHOT=<folder>[,<every>]` writes every n-th picture (default 60) there as `frame_<number>.ppm` (pictures of the game: never commit them; `*.ppm` is ignored).

At build time `qilin lift --files 24` writes the lifted C++ into the build tree (`build/generated/toycommander`, never the source tree), and `toycommander` is linked from it and the library `toycommander_game` (everything else: the game's own code, `dreamcast/`, the runtime; the Windows download ships that library prebuilt, `tools/player-kit`). At run time `toycommander` reads the boot file from the disc dump again, checks that its SHA-256 is the one the program was lifted from (`g_lifted_sha256` in the generated `table.cpp`), and boots it. While the port is being brought up it is built with checked memory (`QILIN_RUN_CHECKED`, on by default), so a stray access stops, naming the instruction.

## The pieces (`recomp/runtime/`)
- **`guest.hpp`:** the context, memory access and the helpers the lifted code calls, and `rt::replaced`.
- **`memory.*`:** 4 GB of host address space reserved for the guest's (`base + addr`), with only what is committed backed: RAM, 16 MB at `0x8C000000`, where the game is linked to use it.
- **`bus.*`:** every access outside that RAM. `ld`/`st` in `guest.hpp` check one range and call the bus otherwise. Below `0xE0000000` the bus decodes the physical address as the SH-4 does (the low 29 bits): RAM's other views (`0xAC000000`, `0x0C000000`, the mirrors) go to the same RAM, and devices are found by physical range. From `0xE0000000` addresses are taken whole: the store queues (`0xE0000000`, flushed by `pref` to where QACR0/1 say) and the SH-4's own registers. Devices are mapped by the program (`rt::map`), with a block write for whole store-queue bursts. An access nothing handles stops, naming the address and the instruction. `QILIN_TRACE_BUS=1` logs every device access.
- **`system.*`:** the registry of native replacements (`provide`), lookups in the function table (`function_containing`), calls from native code into guest code (`call_guest`, with a return address no guest code has), and the report. Every stub `qilin lift` writes for a replaced function calls `rt::replaced`. That runs the native code registered for the address and returns to the caller, as the guest code would; if there is none, it stops as *unregistered*, naming the function and its caller. That is how the bring-up finds the next thing to write.
- **`dispatch.cpp`:** indirect calls through the generated function table.

Native code follows SHC's convention: arguments in r4–r7, the result in r0. It leaves r8–r15 alone, and writes no register its guest counterpart doesn't, since the callers' analysis relies on what each callee writes.

**SR.** Lifted code reads SR and writes its interrupt mask: the middleware masks interrupts around its hardware set-up (`stc sr,r0 ; and ; or #0xF0 ; ldc r0,sr`) in 19 functions. SR is held in the context but for T, S, Q and M, which live in their own locals. The system bits are fixed: privileged mode, register bank 0, exceptions unblocked, the FPU enabled. IMASK is whatever the code sets; the runtime will deliver its interrupts (vertical blank and the like) only where IMASK allows them, as the hardware does. An `ldc` that would change a system bit stops. The differential test covers the four SR forms. That leaves 2 functions unlifted, both setting up exception handling (`stc vbr`, `ldc rN,r1_bank`), which the port replaces.

## The start-up (`toycommander/src/boot.cpp`)
The boot file's entry code sets the cache control register and jumps to Shinobi's start-up at `0x8C0B0340`. The runtime does what that start-up does, natively:
1. The boot file goes to `0x8C010000`; the rest of RAM is zero.
2. r15 is `0x8C00F400`, and `0x8C00C000`–`0x8C00F400` is filled with the word `0x41474553` ("SEGA"), as the start-up fills its stack.
3. The C runtime's sections are set up as SHC's section initialisation does, from four tables of start and end addresses in the image (`0x8C09F5B8`–`0x8C09F5DC` and Shinobi's, `0x8C0C56A0`–`0x8C0C56C4`): two zero-filled, two copied.
4. `0x8C0B068A`, Shinobi's initialisation, is called with r4 = the word at `0x8C0C5690` (`0x8C010000`).
5. Then the game's `main`, `0x8C02796A`.
6. Then `0x8C0B06E2`, Shinobi's exit, with the same r4.

The calls go through the function table, so they reach the registry.

## The GD-ROM: gdFs and gdd lifted, the boot ROM's system calls replaced
Shinobi's file system, gdFs (1.08), is ISO 9660 and handle bookkeeping over a driver table (`0x8C0C5980`, 31 slots); its GD-ROM driver, gdd, is a table of 20 operations (`0x8C0C6260`) over the boot ROM's system calls, which it reaches through 13 one-line wrappers (`0x8C0C1520`–`0x8C0C161C`: `r6` = 0 or −1, `r7` = the call, then a jump through `0x8C0000BC`). None of gdFs or gdd touches hardware: everything goes through those calls, a few of syCache's and syTmr's functions and the interrupt chains. So, as for Kamui 2, the library is lifted and what lies beneath it is the port's: gdFs (`0x8C0B13D4`–`0x8C0B3288`) and gdd (`0x8C0BD264`–`0x8C0BDB14`) are lifted regions, with no unknown bytes, and every handle, directory record and state gdFs keeps is the console's, byte for byte. Replacing gdFs's 26 functions the middleware calls would have meant reconstructing those structures by guesswork.

The calls (`gdrom_bios.cpp`), on the player's own disc dump: commands are done when they are sent, and every request is complete the first time gdd asks. Frame addresses are the disc reader's sectors plus 150 (the lead-in). So far:
- call 0, send a command: 24 (the drive's initialisation), 40 (its version string, of which gdFs reads three digits into a word nothing reads), 16 and 17 (PIO and DMA reads of 2048-byte sectors to a buffer); any other command stops, naming it;
- call 1, a request's state: complete (2), with the bytes transferred;
- call 2, the boot ROM's turn to work, and call 5, the DMA's end: nothing to do;
- call 3, the drive's initialisation; call 4, its state: paused, with a GD-ROM in.

A DMA read ends, on the console, with the system bus's event 0xA40 (GD-ROM DMA end), whose chain gdFs has a handler on. The port raises it at the next system call made with interrupts at level 4 unmasked: after the read was sent and the caller has recorded what it waits for, as on the console, never inside the call that sent it.

## The bring-up so far
Each run stops at the next thing the port doesn't have, as the sister projects found theirs.

1. `0x8C0B068A`, Shinobi's initialisation, called by the start-up: written (above).
2. `0x8C04E8D6`, the middleware's system initialisation, called by `main`: not lifted because of `stc sr`. That led to the SR model (above), which lifts 19 of the 21 functions that weren't.
3. `0x8C0BAB98`, then the five settings queries (`0x8C04E79C` gathers them into a word of flags), then Shinobi's hardware set-up and its allocator: written (above).
4. **Now:** the first hardware access. The middleware's system initialisation calls `0x8C056BC0`, Kamui 2's initialisation. That reaches `0x8C08790C`, which programs the graphics chip through two small helpers, `0x8C084382` (read a register) and `0x8C084378` (write one), and stops reading its ID register at `0xA05F8000`. The call chain is main → `0x8C04E8D6` → `0x8C056BC0` → `0x8C06BE68` → `0x8C08790C` → `0x8C084382`.

**The decision: the hardware under Kamui 2, not Kamui 2's API.** The plan was Kamui 2 replaced at its API, as Punch-Out replaced GX. Trying to name its functions showed that without symbols it can't be done reliably: its objects are interleaved with the engine's and the audio manager's, and its entry points are only told apart by guesswork. So Kamui 2 stays lifted, and the port provides what it drives: the PowerVR2's registers (`pvr.cpp`: the ID and revision the code checks, the interrupt status registers' write-one-to-clear, a register file for the rest), video memory in both its views, and the SH-4's timer 0 (`sh4.cpp`), which Kamui 2 times its waits with. The tile accelerator's parameter stream comes next, decoded into Vulkan 1.3 draws. Register names come from KallistiOS's headers (`prior-art.md`); what each bit does is read from Kamui 2's own code.

5. Kamui 2's whole initialisation now runs lifted against that hardware, and its interrupt registration (`0x8C085E16`, the one Kamui 2 function replaced) records its handler. Open: the display's sync status reads 0, and no interrupt is delivered yet; both are needed once something waits for a frame.
6. Then Shinobi's remaining set-ups called by the system initialisation (`0x8C0B3288`, the clock `0x8C0B4244`), the allocator in full (above: the game's first `malloc`), and gdFs's directory record.
7. `0x8C0B1A46`, gdFs's initialisation, called by the middleware's file layer (`0x8C04D5A2`, retried a few times on failure). Reading gdFs showed it is software over gdd over the boot ROM's calls: gdFs and gdd were made lifted regions and the calls written (above). On the way: the interrupt chains (gdFs adds a handler for the vertical blank and one for the GD-ROM DMA's end), syTmr's reads (gdFs times its waits), syCache's operations (gdd invalidates the cache after a DMA), and a gap in discovery (`0x8C0B1FD6`, a driver-table entry reached by a tail-call branch).
8. gdFs's initialisation, the drive's version and status, its first reads and the middleware's directory loading (`0x8C04D3A4`) now run as on the console. Then the clock (`rtc.cpp`), timer 0's restart, and `main` goes on into its own start-up.
9. Kamui 2 starts a DMA with the SH-4's DMA controller (`0xFFA0002C`, channel 2's control register, from `0x8C09595C`, Kamui 2's DMA dispatcher): its vertex buffers go to the tile accelerator at `0x10000000`. That brought the DMA controller (`sh4.cpp`: a register file; channel 2 only, in the one configuration Kamui 2 uses, `CHCR2 = 0x12C1`), channel 2's transfer on the system bus side (`pvr.cpp`: `C2DSTAT`, `C2DLEN`, `C2DST`; to the tile accelerator or to texture memory; then event 19) and the tile accelerator's decoder (`ta.cpp`).
10. Then Kamui 2 waited (`0x8C0886F4`) for a flag its interrupt handler clears: interrupts were needed. Lifted code now polls at its loops' backward branches (`guest.hpp`), the port's events (DMA ends, lists' ends, renders, the vertical blank) go to Kamui 2's handler at level 6, and its waits end. `QILIN_TIMEOUT` found the loop.
11. **Now:** `0x8C0B367E`, Shinobi's peripheral server, called every frame. Its records (24 of 52 bytes, the controllers' state the game reads: buttons on, off, pressed, released, the triggers and sticks) are Shinobi's peripheral library (pd) over its Maple bus driver, which drives the Maple bus's DMA. The same reasoning as for gdFs applies: lift pd and the Maple driver, and provide the Maple bus (controllers from SDL3, the memory card as a file, the Jump Pack as rumble).

12. pd, bu and the Maple driver are lifted regions now (`layout.cpp`), as gdFs is: their records are the console's by construction. The peripheral server runs every vertical blank; the Maple bus's DMA registers (`0x005F6C00`–) are still only the register file's, so no device answers yet.
13. **Now:** bu's initialisation (`0x8C0B0780`, called by the audio manager's set-up) starts its server as a coroutine: `0x8C0C4774`–`0x8C0C4B4A` is a small thread library, with a stack per thread and a switch by a full context save (`0x8C09CDCC`) and restore (`0x8C09CD58`), a `setjmp`/`longjmp` of every register. Lifted code runs on the host's stack, so a guest context switch can't be followed as calls: the thread library is replaced, with a host-side cooperative thread per guest thread, each running lifted code on its own `Context`, one at a time.

14. bu's thread library is lifted (`0x8C0C4774`–`0x8C0C4A3A`) but for the scheduler's pass (`0x8C0C4A7C`) and a thread's yield (`0x8C0C4A3A`), natives in `threads.cpp`: each guest thread runs on a host thread with its own context, handing over at exactly the guest's switches. A thread starts from the registers its creation saved in its record (its stack, and its entry in PR); the pass runs every ready thread whose tick has come, starting again from the first after each yield as the guest's does; a thread to kill is marked dead and its host thread unwound when its slot is freed (by the lifted `0x8C0C48E6`). The save (`0x8C09CDCC`) stays lifted: creating a thread uses it to fill the record; the restore is never reached.
15. The audio manager's set-up (`0x8C06AA86`, amInit, from the engine's sound set-up `0x8C04A0FA`) writes the sound chip. Sound RAM (2 MB at physical `0x00800000`) and the chip's registers (`0x00700000`, a register file) are mapped now (`aica.cpp`); the chip's ARM is never started.
16. **Now:** amInit's driver install (`0x8C0833B8`, acSystemInstallDriver) holds the ARM in reset (`0xA0702C00` bit 0), copies `AUDIO64.DRV` into sound RAM, releases the ARM and waits for the driver to write a pointer to its interface into sound RAM (the loop at `0x8C083490`). Nothing runs the driver, so it waits for ever (`QILIN_TIMEOUT` finds it).

17. The driver's start-up handshake (`aica.cpp`: releasing the ARM's reset writes `0x30040` to `0xB408` and `0xEC`, as the driver does) lets amInit finish: the audio manager's own commands don't wait for an answer in its set-up. Then the engine's set-up goes on through CD audio (the GD-ROM's commands 20, play, and 22, pause, and 19, the table of contents, from the disc reader's tracks: `gdrom_bios.cpp`), the peripherals' vibration and screen drivers (lifted, `0x8C0BAE40`–`0x8C0BAF20` and `0x8C0C17C4`–`0x8C0C1C0C`), and into the first movie: the movie player clears the operand cache through its address array (`0xF4000000`, accepted as a no-op: `sh4.cpp`).
18. **Now:** the TrueMotion decoder's block dispatcher (`0x8C09F2AC`) reads a pointer from its state (`+0x10BC`) that holds 0x90, a block size, and stops reading address 0x90. The dispatcher's handlers (a table at `0x8C0A3CDC`) run with SZ = 1, which the FPSCR pass now follows (the layout names the table: `indirect_targets` in `layout.cpp`); that changed only one instruction's mode and not the stop. What fills that state wrongly is open: a comparison with the console's RAM at the same point (Flycast's libretro core as a black box exposes the system RAM) is the likeliest way to find it, since the port's allocator puts every block where the console's does. `QILIN_DUMP=<address>,<bytes>` prints guest memory at a stop.

**Comparing with the console's RAM** (`qilin_dcref <core> --game <disc> <frames> <every> <prefix>`: the game in Flycast's libretro core with its own BIOS replacement, run as a black box, its 16 MB of RAM written every few frames; `QILIN_RAM_DUMP=<file>` writes the port's at a stop; both outside the repo). What it showed at step 18:
- The port's heap is the console's: the movie decoder's state is at `0x8C8A1778` in both, and of the heap's 64 KB blocks, all but those the movie's buffers fill (which depend on timing) are byte for byte the same. Every file read and every allocation so far agrees.
- On the console the decoder starts at about frame 75 and writes pointers into `0x8C8A1A20` (`+0x2A8`) and `+0x2B4`/`+0x2B8` (a handler, `0x8C09CE38`, and 8), which the port's run never does; `+0x10BC` holds 0x90 on the console too, so the dispatcher can't be reading its pointer from there on the console: the console reaches the dispatcher with other registers, or not by this path. `+0x1084` (written once from the frame height: `-(height) - 1`) is −481 on the console and +481 in the port's run, which looks like the first wrong value; whether it is wrong at that moment or changed by the decode isn't settled yet (the dumps are at frame boundaries, the port's at the stop).
- **Found:** comparing the console's code with the boot file showed three halfwords changed at run time, `0x8C09F320`–`0x8C09F324`: the decoder's set-up (`0x8C09EA20`) rewrites the offsets in its dispatcher's literal pool (`0xE1C`, `0xE18`, `0xDD4` become `0xDBC`, `0xDB8`, `0xDB4`). The lifter had folded the image's values into the code. Discovery now marks a literal as patched when a function loads its address as a constant (`Cfg::patched_literals`: 23 on this build, the three among them; the others cost one load each), and the lifter reads those from memory. **The audio manager: where to cut.** The audio manager names its functions in its messages (`am*`, `ac*`: 79 functions found that way). No MIDI (the music is CD audio). Two ways on:
- **The driver's mailbox** (the same reasoning as gdFs's and Kamui 2's): keep the whole audio manager lifted, and answer what the ARM driver would, natively: at start-up the pointer to its interface area (inside the driver image the audio manager has copied), then the commands the `ac*` functions queue in sound RAM (each one's layout can be read from the function that builds it), the acknowledgement flags they wait on, and the ports' state that `acDigiGetCurrentReadPosition` reads; the voices are then mixed natively from sound RAM. Exact for everything the audio manager keeps, but it means working out the interface from both sides.
- **The API:** replace the 21 functions above natively (amInit setting what the lifted `am*` functions check, and initialising the lifted heap), with the voices in the port's own state. Less to work out, but the heap's and the ports' guest state would be the port's guess.

The first is the boundary the rest of the port follows; it is the plan unless the interface proves too wide.

**What the driver's side looks like** (read from `AUDIO64.DRV` on the player's disc with a disassembler; nothing of it is run or copied). The image starts with ARM exception vectors and a version string; at `0xC0`–`0xE8` it has a table of the interface's offsets in sound RAM, which the audio manager reads after the install: `0xBF00`, `0xB600`, `0xB400`, `0xC000`, `0xB200`, `0xC800`, `0xBE00`, `0x100`, `0x1468`, `0x14A8`, `0x14F0`. `0xEC` is 0 in the image. At start-up the driver sets its stack, sets two of the chip's registers, writes `0x30040` (where the sound RAM it doesn't use begins) to both `0xB408` and `0xEC`, and loops: when the byte at `0xB400` (the command flag) is non-zero it handles the command (from `0x39A0`), and it does its per-frame work (`0x4AA8`). The audio manager's install waits for `0xEC` to be non-zero, clears the word at that offset, and keeps the other offsets for its commands. So the port's "driver" starts as that handshake, then handles the commands the audio manager sends through `0xB400`, as the driver's handlers do, for the commands the engine uses.

**The driver's commands and the chip** (`aica.cpp`, `sound.cpp`). Read further in `AUDIO64.DRV` (disassembled, nothing copied): the command loop clears the flag at `0xB400` first, takes slots from where it stopped while their first byte isn't 0, logs each (its first 12 bytes and the word at `0xB410`) to a 2 KB ring at `0xC800` (next entry's offset at `0xB40C`, the entry after the newest all ones), and frees a slot by clearing its first two bytes. Codes `0x80`–`0xAF` and `0x00`–`0x3F` go through two jump tables. A port is a channel of the chip: the driver keeps a copy of each channel's 18 registers at `0x1B38 + 0x48 n`, set at start-up from a template in its image (`0x1AF0`: full level, centred, the fastest envelope) and by close (`0x91`), and edits the copy, writing the chip's registers when a command takes effect:
- open (`0x90`): the start address (the SH-4's address's bits 22-0), PCMS (`[12]`: 0 16-bit PCM, 1 8-bit, 2 ADPCM), the loop's end from the size in bytes (`[8]`, in samples, less one), the loop's start 0, the pitch (`[13]`, high byte first: OCT and FNS);
- play (`0x93`): the loop flag (`[8]` bit 0) and, if `[12]` isn't 0, the loop's start (its low half) and end; key off, every register, key on; the port's byte at `0x1468` to 0xFF, its position at `0x14F0 + 4 n` to 0 and the one before at `0x15F0 + 4 n` to all ones;
- stop (`0x94`), play and stop several (`0x9C`, `0x9D`: [4] ports 32-63, [8] 0-31, the keys on all at once), level (`0x96`: DISDL), pan (`0x97`: the game's 0-31 with 16 the centre, made DIPAN), sends (`0x95`), the sample rate (`0xAC`: [4] FNS, [8] the octave; `0x98` the same relative to the copy, to the chip only), play with parameters (`0xAD`: level, pan, sends, an optional position event, play with [12] as the loop's points, then a pitch with a flag for absolute);
- a message to the SH-4 (`0x9E`: a byte into a 64-byte ring at `0x14A8`, next at `0xE4`, then the chip's interrupt, the system bus's external event 1, which the audio manager chains as event 0xB20), the interrupt alone (`0x9F`); CD audio's level and pan (`0x35`, `0x36`: the external inputs' EFSDL and EFPAN) and its set-up (`0x3E`).
The driver's per-frame work reads each playing channel's position into `0x14F0` (the old one into `0x15F0`) and keys off a channel without a loop that has stopped, clearing its byte at `0x1468`. The stand-in does all of this in the same records; the per-frame work runs when the guest reads those records and every 5 ms. Position events (`0x92`, and `0xAD`'s `[8]`): the position goes to `0x16F0 + 4 n` and the port's bit is set at `0x14E8` (ports 0-31) or `0x14EC` (32-63); each frame, after the positions, a pending port whose channel has passed it since the last frame (a signed comparison, allowing for a loop back) posts its number as a message, as `0x9E` does, and its bit is cleared. Toy Commander never asks for one; Toy Racer does.

**Two versions of the driver.** Toy Racer's `AUDIO64.DRV` is version 1.90h.2 (2000-06-28), Toy Commander's 1.80d.2 (1999-09-27): the same design, its records lower in sound RAM (positions at `0xC34`, the previous ones at `0xD34`, the active bytes at `0xBAC`, messages at `0xBEC`, events at `0xE34` with their bits at `0xC2C`, the template at `0x1234`, the copies at `0x127C`), and these differences, read from both disassemblies side by side: open (`0x90`) closes the port first and sets its previous position to all ones; level (`0x96`, `0xAD`'s `[3]`) sets the total level (TL, an attenuation: word 10's high byte; its audio manager sends 255 minus the volume) where 1.80's sets the direct level; the sends (`0x95`'s `[5]`, `0xAD`'s `[10]`) also set the direct level; `0xAD`'s event is `[8]`'s low half; stops (`0x94`, `0x9D`) drop a port's pending event; the event check skips a port that started since the last frame; the CD set-up (`0x3E`) leaves both inputs silent until a level (`0x35`), and the start-up runs it; `0x9E` frees its slot before it returns (nothing the SH-4 does can tell). The stand-in knows which it stands for from the table of offsets each image publishes at `0xE0`–`0xE8` (`0x1468`, `0x14A8`, `0x14F0`; `0xBAC`, `0xBEC`, `0xC34`), and stops on any other.

The port's chip (`sound.cpp`) plays the channels from those registers, as the chip does: keyed on and off by KYONB when KYONEX is written; 16-bit and 8-bit PCM and Yamaha's 4-bit ADPCM (the YMZ280B data sheet's algorithm: a step scaled by 230-614/256 by the nibble's size, low nibble first; a loop goes back to the decoder's state at the loop's start), linearly interpolated at 44.1 kHz × 2^OCT × (1 + FNS/1024); the loop's start and end; DISDL, DIPAN and TL; the master volume. No envelopes (the template's are instant), no DSP effects (the sends are kept, not heard). CD audio comes in on the two external inputs: the drive's play (command 20, by track numbers, with repeats; pause 22, go on 23) runs 75 frames a second and its samples come from the dump's audio tracks (`Disc::read_audio`); the subcode's position is where it is. All of it runs by guest time under one lock: a read of a position renders up to that moment first, so the movie player's waits see the chip move exactly as time passes; the mixer thread renders up to the present every 5 ms into the host's sound output (`host/`'s `AudioOut`; none with `QILIN_HEADLESS`) and into `QILIN_WAV=<file>`. `QILIN_TRACE_SOUND` prints each command.

**Interrupts.** An interrupt comes between two instructions; lifted code keeps registers in locals and can't be stopped just anywhere. So the lifter puts a poll at every backward branch: `QILIN_POLL_IRQ(r15)` tests `rt::g_irq_pending` (a relaxed atomic load, set by any event and by the 60 Hz video clock's thread) and, if set, passes the stack pointer and calls the service. The service raises the vertical blank's events (3 and 4) if a frame of guest time has passed, then, while IMASK is below 6 and an event enabled in IML6 (`0x005F6930`/`34`/`38`) is pending, calls Kamui 2's handler with IMASK 6, putting every register back afterwards; the handler takes one event per call and acknowledges it. Pending events that IMASK holds back wait for an `ldc` that lowers it. Every loop reaches a poll; straight-line code between two loops doesn't take interrupts, which on the console it could, but no code here relies on being interrupted outside a loop.

**The renderer** (`renderer.cpp`, `texture.cpp`, `video.cpp`, `shaders/`). STARTRENDER (`0x005F8014`) draws the scene the tile accelerator has taken with Vulkan 1.3 into its frame buffer, as the console's renders end at once, and the vertical blank shows the frame buffer the display reads (`FB_R_SOF1`). A frame buffer is an image kept from render to render, known by its address (`FB_W_SOF1`), because a frame can be rendered in parts: Toy Racer's races render lines 0-447 and then 447-478, each render clearing and drawing only inside its frame buffer clip (`FB_X_CLIP`/`FB_Y_CLIP`). Its size is what the display reads (`FB_R_SIZE` at `FB_R_CTRL`'s depth, doubled when interlaced), at least the clip, and it only grows: Toy Racer's second part reaches a line the first doesn't (478 against `FB_R_SIZE`'s 477), and recreating the image at each part's size lost the other part (half the pictures black). Growing makes the device go idle before the old image goes, since the display may still be showing it. Triangles with a vertex beyond a million pixels or not a number are dropped (llvmpipe's rasteriser crashed on one in a race). A scene becomes one vertex buffer of triangles and a list of draws on the CPU: strips are expanded there, culled by the ISP word's rule and flat-shaded (the triangle's last vertex colours it), so the pipelines are few, one per blend state, with the depth compare and write as dynamic state. Vertices keep the hardware's coordinates: x and y in the game's pixels and z = 1/w, so the vertex shader sets clip w = 1/z and the GPU interpolates as the PowerVR2 does (perspective-correct); depth is z, larger nearer, cleared to 0, and the ISP word's depth modes are Vulkan's compare ops in the same order. The order is the background plane (three vertices in parameter memory at `ISP_BACKGND_T`, drawn as their parallelogram at `ISP_BACKGND_D`'s depth), then the opaque, punch-through and translucent lists, each as sent. The fragment shader is the TSP's: the four texture shading instructions, the offset colour, "use alpha" and "ignore texture alpha", and punch-through's alpha reference (`PT_ALPHA_REF`). Textures are decoded on the CPU from video memory as the texture hardware addresses it (the 64-bit view) and the TSP and texture control words: ARGB1555, RGB565, ARGB4444, YUV422, 4- and 8-bit palettes (in the palette RAM's four formats), twiddled, raster and stride, vector quantised, mip-mapped (the largest level). A texture is decoded again only when a page of video memory under it, or its palette entries, changed (`vram64_generation`: a counter per 4 KB page). Not drawn yet, each named once on stderr when a scene asks for it: modifier volumes (shadows), fog, a polygon's second volume, the translucent list's per-pixel sorting (it is drawn in the order sent), mip-mapping below the largest level, the user tile clip. `toycommander_render_test` checks the decoder's formats and draws a scene headless (skipped where there's no Vulkan 1.3 device, as on CI).

**The tile accelerator** (`ta.cpp`). The stream Kamui 2 sends to `0x10000000` (by DMA, or by store queue) is decoded into a scene: strips of vertices with the ISP/TSP instruction, TSP and texture control words (per volume, for two-volume polygons), sprites as strips of four, and modifier volumes' triangles. Vertex layouts follow the last global parameters (colour type, texture, 16-bit UVs, two volumes); packed colours become floats, intensities are multiplied by the face colours. Each list's end raises its event (7, 8, 9, 10, 21). `TA_LIST_INIT` starts a new scene; `STARTRENDER` will hand it to the Vulkan renderer (for now it counts the render and raises the render's ends, events 0-2).

The report now ends with the call chain: SHC keeps no frame pointers, but every function that calls saves PR on the stack, so the stack's return addresses (words where the instruction four bytes earlier is a call) are the chain. `QILIN_STACK=1` dumps the whole stack too.
