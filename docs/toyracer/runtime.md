# The runtime and the bring-up

What runs the lifted program: guest memory, the registry of native replacements, the start-up, and the stops that say what to write next. All of it is Toy Commander's runtime (ToyCommander--QilinRecomp, `docs/runtime.md`), brought over in v0.2.0: the two games use newer and older versions of the same libraries, and most of their functions are the same code at other addresses (below). The game's program is `toyracer` (it was `qilin_run` in its own repository: `docs/naming.md`).

## Building and running
The program is built only from the player's own boot file, as Punch-Out's is from its `main.dol`:

```sh
build/qilin extract path/to/game.cue --out extracted        # outside the repo, or in an ignored folder
cmake -S . -B build -DQILIN_TOYRACER_BOOT=extracted/files/1TOYRACE.BIN   # or the disc's .cue
cmake --build build --target toyracer
build/toyracer path/to/game.cue
```

At build time `qilin lift --files 24` writes the lifted C++ into the build tree (`build/generated/toyracer`, never the source tree), and `toyracer` is linked from it and the library `toyracer_game`. At run time `toyracer` reads the boot file from the disc dump again, checks that its SHA-256 is the one the program was lifted from (`g_lifted_sha256` in the generated `table.cpp`), and boots it. While the port is being brought up it is built with checked memory (`QILIN_RUN_CHECKED`, on by default), so a stray access stops, naming the instruction.

## The pieces (`recomp/runtime/`)
- **`guest.hpp`:** the context, memory access and the helpers the lifted code calls, and `rt::replaced`.
- **`memory.*`:** 4 GB of host address space reserved for the guest's (`base + addr`), with only what is committed backed: RAM, 16 MB at `0x8C000000`, where the game is linked to use it.
- **`bus.*`:** every access outside that RAM. `ld`/`st` in `guest.hpp` check one range and call the bus otherwise. Below `0xE0000000` the bus decodes the physical address as the SH-4 does (the low 29 bits): RAM's other views (`0xAC000000`, `0x0C000000`, the mirrors) go to the same RAM, and devices are found by physical range. From `0xE0000000` addresses are taken whole: the store queues (`0xE0000000`, flushed by `pref` to where QACR0/1 say) and the SH-4's own registers. Devices are mapped by the program (`rt::map`), with a block write for whole store-queue bursts. An access nothing handles stops, naming the address and the instruction. `QILIN_TRACE_BUS=1` logs every device access.
- **`system.*`:** the registry of native replacements (`provide`), lookups in the function table (`function_containing`), calls from native code into guest code (`call_guest`, with a return address no guest code has), and the report. Every stub `qilin lift` writes for a replaced function calls `rt::replaced`. That runs the native code registered for the address and returns to the caller, as the guest code would; if there is none, it stops as *unregistered*, naming the function and its caller. That is how the bring-up finds the next thing to write.
- **`dispatch.cpp`:** indirect calls through the generated function table.

Native code follows SHC's convention: arguments in r4–r7, the result in r0. It leaves r8–r15 alone, and writes no register its guest counterpart doesn't, since the callers' analysis relies on what each callee writes.

**SR.** Lifted code reads SR and writes its interrupt mask: the middleware masks interrupts around its hardware set-up (`stc sr,r0 ; and ; or #0xF0 ; ldc r0,sr`) in 19 functions. SR is held in the context but for T, S, Q and M, which live in their own locals. The system bits are fixed: privileged mode, register bank 0, exceptions unblocked, the FPU enabled. IMASK is whatever the code sets; the runtime will deliver its interrupts (vertical blank and the like) only where IMASK allows them, as the hardware does. An `ldc` that would change a system bit stops. The differential test covers the four SR forms. That leaves 2 functions unlifted, both setting up exception handling (`stc vbr`, `ldc rN,r1_bank`), which the port replaces.

## The start-up (`shinobi/src/boot.cpp`, shared with Toy Commander since its runtime log's step 52)
The boot file's entry code sets the cache control register and jumps to Shinobi's start-up at `0x8C0C5440`. The runtime does what that start-up does, natively:
1. The boot file goes to `0x8C010000`; the rest of RAM is zero.
2. r15 is `0x8C00F400`, and `0x8C00C000`–`0x8C00F400` is filled with the word `0x41474553` ("SEGA"), as the start-up fills its stack.
3. The C runtime's sections are set up as SHC's section initialisation does (`0x8C0C5480`), from four tables of start and end addresses in the image (`0x8C0A5B04`–`0x8C0A5B28` and Shinobi's, `0x8C0F9BC4`–`0x8C0F9BE8`): two zero-filled, two copied. The zero-filled data ends at `0x8C1D9D68`.
4. `0x8C0C5856`, Shinobi's initialisation, is called with r4 = the word at `0x8C0F9BB4` (`0x8C010000`).
5. Then the game's `main`, `0x8C0204E4`.
6. Then `0x8C0C58AE`, Shinobi's exit, with the same r4.

The calls go through the function table, so they reach the registry.

## Finding Toy Commander's functions here
Toy Commander's bring-up had already named and replaced two dozen functions. Their counterparts here were found by the code itself, not by guesswork: each function's instruction words, with the fields that depend on where it was linked masked out (PC-relative displacements, branch displacements), hashed. A hash that occurs once in each boot file pairs two functions: **1,322 pairs**. The paired functions' literal pools then pair the data: the n-th literal of one is the n-th of the other, which gives 2,131 addresses in all (the allocator's state, Kamui 2's, the tables). Every native below that came from Toy Commander was moved through that map and its constants checked against this boot file's code. This is a working method, done with scripts outside the repository, since its inputs are both games' boot files; it is described here so it can be repeated.

What it showed besides: here some of Shinobi's parts are linked among the middleware (the timer set-up `0x8C04D758`, the cable query `0x8C04DB04`), so they are lifted unless listed as replaced (`recomp/src/layout.cpp`).

## The GD-ROM: gdFs and gdd lifted, the boot ROM's system calls replaced
Shinobi's file system, gdFs (1.10), is ISO 9660 and handle bookkeeping over a driver table (`0x8C0FA004`, 31 slots); its GD-ROM driver, gdd, is a table of 20 operations (`(Toy Commander's 0x8C0C6260)`) over the boot ROM's system calls, which it reaches through 13 one-line wrappers (`0x8C0D5D20`–`0x8C0D5E1C`: `r6` = 0 or −1, `r7` = the call, then a jump through `0x8C0000BC`). None of gdFs or gdd touches hardware: everything goes through those calls, a few of syCache's and syTmr's functions and the interrupt chains. So, as for Kamui 2, the library is lifted and what lies beneath it is the port's: gdFs (`0x8C0C7D30`–`0x8C0C9BE8`) and gdd (`0x8C0D18B4`–`0x8C0D216C`) are lifted regions, with no unknown bytes, and every handle, directory record and state gdFs keeps is the console's, byte for byte. Replacing gdFs's 26 functions the middleware calls would have meant reconstructing those structures by guesswork.

The calls (`gdrom_bios.cpp`), on the player's own disc dump: commands are done when they are sent, and every request is complete the first time gdd asks. Frame addresses are the disc reader's sectors plus 150 (the lead-in). So far:
- call 0, send a command: 24 (the drive's initialisation), 40 (its version string, of which gdFs reads three digits into a word nothing reads), 16 and 17 (PIO and DMA reads of 2048-byte sectors to a buffer); any other command stops, naming it;
- call 1, a request's state: complete (2), with the bytes transferred;
- call 2, the boot ROM's turn to work, and call 5, the DMA's end: nothing to do;
- call 3, the drive's initialisation; call 4, its state: paused, with a GD-ROM in.

A DMA read ends, on the console, with the system bus's event 0xA40 (GD-ROM DMA end), whose chain gdFs has a handler on. The port raises it at the next system call made with interrupts at level 4 unmasked: after the read was sent and the caller has recorded what it waits for, as on the console, never inside the call that sent it.

## The bring-up so far
Each run stops at the next thing the port doesn't have, as the sister projects found theirs. **Toy Commander's log has how each piece was understood and designed**; almost all of this runtime is that project's, moved here through the code match, so this log only says what happened here.

1. With Toy Commander's natives and its hardware under Kamui 2 moved across, the first run went from the start-up through `main` (`0x8C0204E4`) and the middleware's system initialisation (`0x8C05DAFE`) into Kamui 2's initialisation (`0x8C065F64`), and stopped in the compiler's structure copy (`0x8C04DE3C`): written natively, here.
2. gdFs's initialisation (`0x8C0C83A2`): Toy Commander's GD-ROM work (gdFs and gdd lifted over the boot ROM's calls, the interrupt chains, the clock) came across and ran first time on this game's disc.
3. `0x8C0C54DA`, which `main` calls next: the C runtime's initialisation lists, whose entries are the modem library's static constructors. Written here; Toy Commander has no such list.
4. Kamui 2's first DMA, the tile accelerator's input, the display's timing and the graphics interrupt. These were written here first, and by Toy Commander's session at the same time; **this project now uses Toy Commander's versions** (`interrupts.*`, `ta.*`, its `pvr.cpp` and `sh4.cpp`, interrupts taken at loops' backward branches), and its own were dropped. The game's graphics start-up completes: textures load, display lists are decoded, frames go by. There is no renderer yet.
5. Shinobi's peripheral library, memory-card file system and Maple driver, lifted as in Toy Commander (the regions found by matching its functions: `recomp/src/layout.cpp`). Here the peripherals' set-up goes on to Shinobi 1.71's extension check (`0x8C0D0DC0`), which looks for the modem: answered natively with "nothing there".
6. The audio manager's initialisation: `main` calls `0x8C0591BC`, which reaches `acSystemInit` (`0x8C082630`) and `acSystemInstallDriver` (`0x8C0827D4`), the sound driver's installation into the sound chip's memory. Toy Commander's sound RAM and sound chip registers (`aica.*`) and bu's threads on host threads (`threads.*`; the library is at `0x8C0E0BC8`–`0x8C0E0F9E` here) came across, and the installation runs.
7. The audio set-up goes on to the CD: gdFs (`0x8C0C8D08`, called from `0x8C058B8E`) sends the drive command 22 (CD audio's pause). Toy Commander's bring-up wrote the CD audio commands (20, 21, 22) soon after, and they came here through the code match.
8. Shinobi's keyboard library (pdKbd, `0x8C0C5924`–`0x8C0C5AFC`) is lifted like pd: it is software over the Maple driver, and the game initialises it.
9. The menu polls the drive's audio status: gdFs (`0x8C0C8A34`, called from `0x8C058A10`) sends the drive command 34, sub-channel data. Toy Commander's bring-up hadn't met it, so it was written in Toy Commander's repo (`gdrom_bios.cpp`'s `write_subcode`: format 1, 14 bytes of Q-channel data from the CD audio state) and moved here, which is how a missing shared piece is handled now: written there, so there is one copy, not waited for.
10. The game is in its own main loop, in the menu (`trmenu.c`): `main` → `0x8C05E700` → `0x8C05E6C2` → `0x8C01FE7C` → `0x8C03871C`, waiting for each frame in Kamui 2 (`0x8C093212`).
11. **The first pictures.** The Vulkan 1.3 renderer of the tile accelerator's scenes was written in Toy Commander's repo (its `docs/runtime.md`, "The renderer") and moved here with the host layer (`host/`, the sister projects' window, device and display), the shaders and the render test. Toy Commander's answer to the sound driver's mailbox came across at the same time. The run draws the start-up screens and reaches the title screen, "Press START button" blinking, and waits there.
12. The title screen waited for Start: the Maple bus's devices. Written in Toy Commander's repo (`maple.cpp`: port A a standard controller from the host's first pad and the keyboard) and moved here.
13. Start was still ignored, though the engine's per-port record (`0x8C1A413C`, filled by `0x8C0738BA`) held it: the game names devices by their product name and compares it with "Dreamcast Controller" and "Racing Controller" (strings at `0x8C0A64A0` and `0x8C0A64B8`), taking no input from a pad it doesn't recognise. The port's controller now reports the standard pad's name (a change in Toy Commander's repo; Toy Commander doesn't check).
14. Through the memory-card warning ("No VM connected", B to go on), the main menu and the race options, a race started, then the process died in llvmpipe's rasteriser: the race renders each frame in two parts, lines 0-447 and 447-478, into the two frame buffers in turn, and the renderer recreated its target at each part's size. Each frame buffer is now an image of its own, kept from render to render, drawn only inside each render's clip, and shown at the vertical blank when the display reads it; it only grows (the second part reaches one line further). Written in Toy Commander's repo.
15. The drive's release command (23, CD audio going on after a pause): Toy Commander's bring-up wrote it the same hour.
16. **Now:** the game races: the car drives with the right trigger, the lap clock runs, the track, the cereal boxes and the progress bar at the bottom are drawn. Next: sound (the audio manager's voices, CD audio from the dump's tracks), the memory card, more pads and the Racing Controller (a wheel through SDL3), then what the renderer lacks (shadows, fog, translucent sorting).

**Seeing it.** `toyracer` opens a window; `QILIN_HEADLESS=1` draws without one, `QILIN_SCALE=<n>` sets the host pixels per game pixel, and `QILIN_SHOT=<folder>[,<every>]` writes every n-th picture as `frame_<number>.ppm` (pictures of the game: never commit them; `*.ppm` is ignored). `QILIN_PRESS` scripts the controller by picture (about 60 a second): `QILIN_PRESS="start@1000-3000/60,b@3100-3400/60,a@3500,start@3800-4300/80,rt@5000-9000/20"` reaches a race and drives in it. On Windows (2026-11-25, `docs/runtime.md` step 49) the race starts by picture 1,350, so that script pauses it; `QILIN_PRESS="start@1000-1300/60,rt@1500-9000/20,left@2400-2600/20,right@3200-3400/20"` drives instead.

**Keep the two bring-ups in step, and let Toy Commander's lead.** Its session writes the shared runtime; this project moves it across with `port`-style scripts (kept outside the repository: they read both boot files), then reapplies the few things only this game has (the structure copy, the initialisation lists, the modem's static objects, the extension check, the European console's settings, this build's layout and start-up). Writing a shared piece here first means writing it twice.

- **The last four** (2026-11-22): `0x8C0CA770` and `0x8C0CA8DC` are not DMA but Shinobi's copies over the G2 bus by the CPU (a unit of 1, 2 or 4 bytes and a step on each side, bracketed by the bus helpers the Maple driver uses), so they are lifted (`0x8C0CA770`–`0x8C0CAAF0`); `0x8C0D636C` and `0x8C0D6464` register and remove an expansion port device's callback on event 0xB60, which only a network library whose open found a device reaches (`0x8C04E768`: the extension check's answer, `0x8C0D0F40`, is -1 here, and it gives up with -40), so their natives stop. Every replaced function Toy Racer's lifted code can reach now has a native (`tools/check/check_natives.py`).
