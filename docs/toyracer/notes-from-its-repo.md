# CLAUDE.md

Static recompilation of **Toy Racer** (Dreamcast, Europe: `MK-5114950`, `V1.050`) to native code. Same requirements and scope as the sister projects (the owner's instruction, 2026-11-21: "Exact same as the other projects, in scope and requirements. learn from what we have done with the other projects, everything is the same in what i want even down to the same enhancements menu etc"). The nearest sister is Qilin1066/ToyCommander--QilinRecomp: the same console, studio and engine, and this project's core is its core at v0.8.0. When a design question here is undecided, do what Toy Commander did, then what the others did (GBTGhoulies--QilinRecomp, PunchOutWii--QilinRecomp, RhythmHeavenFever--QilinRecomp (Beat the Beat), ApbArcade--QilinRecomp); BeatTheBeat's `CLAUDE.md` has the longest list of lessons.

## Requirements (non-negotiable)

- **Efficiency first, then accuracy, and fail loudly.** Never paper over an unknown: stop with a clear error (exit codes, CMake `FATAL_ERROR`, `rt::Stop`).
- **C++23** everywhere: recompiler, runtime and generated code.
- **Vulkan 1.3 only** for graphics. No OpenGL, D3D or Metal backends (macOS goes through MoltenVK).
- **Static recompilation only.** No interpreter, JIT or emulator at run time, not even as a fallback. That includes the sound driver's ARM code (the audio manager is replaced above it) and the modem: there is no online mode (the owner, 2026-11-21: "no online mode"), so the network libraries are replaced by "not connected" and nothing of them is ever run or emulated.
- Targets: 64-bit **Windows, Linux, macOS** on **x86-64 and ARM64**. The low-end reference is ARM boards like the **Raspberry Pi 4**. No 32-bit.
- Compiler minimums: GCC 14, Clang 19, Apple Clang (Xcode 16), MSVC 2022 17.10.
- **Everything unarguably legal** (the owner, for Toy Commander, 2026-11-21: "i want everything unarguably legal"). No GPL code, tables or constants from others (no Dreamcast emulator's, not QEMU's), even though this project is GPL-3.0 itself: they may be run as black boxes, never read into this code, and their outputs never become tables here (so `fsca` computes its values rather than taking Flycast's). No Dreamcast BIOS anywhere. Hitachi's and Sega's documents are cited by title, not linked, quoted or included. Keep dependencies to the fewest possible; third-party libraries (SDL3, Vulkan headers, Dear ImGui for the menu, when they arrive) are permissive and handled as the sister projects handle them.
- Never commit game data or anything derived from it: disc images, `1TOYRACE.BIN`, extracted files, listings, `gen/`, `cfg.json`, symbol lists made from the binary. These are gitignored.

## Layout

- `recomp/src/`: `gdrom` (Redump cue/bin reader, bootstrap, ISO 9660), `bootfile` (loader, known-build SHA-256), `sha256`, `decoder` (SH-4, table-driven, X-macro `QILIN_SH4_OPS`), `cfg` (function discovery, constants, switches, tail calls, far branches, coverage; `cfg_report.cpp` is its text and JSON), `layout` (the supported build's regions, with plans), `hwaccess` (hardware accesses at constant addresses), `fpmode` (FPSCR mode per FPU instruction, interprocedural, per entry-mode context), `lifter` (one function to C++) and `lift_output` (`qilin lift`'s files), `main.cpp` (the `qilin` CLI).
- `recomp/runtime/`: `guest.hpp` (context, memory, helpers), `dispatch.cpp` (calls through the function table), `memory.*` (the 4 GB reservation), `bus.*` (everything outside RAM: devices are mapped with `rt::map`), `system.*` (the registry of native replacements, `call_guest`, the stop report).
- `toyracer/src/`: `qilin_run` (`main.cpp`), the native start-up (`boot.cpp`), the native replacements (`natives.cpp`, `heap.cpp`), the hardware under Kamui 2 (`pvr.cpp`, `sh4.cpp`, `clock.cpp`). Built only with `-DQILIN_GAME_BOOT=<1TOYRACE.BIN>`; `docs/runtime.md` has the design and the bring-up log. `gdrom`, `bootfile` and `sha256` are runtime code too (target `qilin_disc`): no `std::format` there.
- `host/`: the sister projects' window, Vulkan 1.3 device, display, sound output and data folder (from Toy Commander, which took it from PunchOutWii--QilinRecomp). `toyracer/src/renderer.cpp`, `texture.cpp`, `video.cpp` and `toyracer/shaders/` are Toy Commander's, moved by `port.py` (which now copies `host/`, `tools/build_shaders.py` and the game's `shaders/` and `tests/` too).
- `recomp/tests/tests.cpp`: unit tests (`ctest`), no game files. `lift_programs.hpp` (a small assembler and synthetic programs), `lift_gen.cpp` (lifts them at build time), `lift_run.cpp` (runs the lifted code against reference results): the end-to-end lifter tests, which make CI compile generated code with every compiler. `difftest/`: the differential test (`gen.cpp` lifts random encodings of every lifted instruction at build time, `ref.cpp` is the reference interpreter, separate from the lifter, `run.cpp` compares everything). After changing the lifter, run it; a planted bug must fail it.
- `tools/check/verify_decoder.py`: the decoder against Capstone, the whole encoding space.
- `tools/dcref/`: `qilin_dcref`, the FPU's approximate instructions against Flycast's libretro core run as a black box (`fetch.sh` downloads it outside the repo; `-DQILIN_DCREF=ON -DQILIN_DCREF_DIR=<folder>`; Linux x86-64, Mesa EGL surfaceless).
- `docs/`: design and results. Keep them current. `roadmap-and-design-targets.md` is the roadmap; `disc-analysis.md` the disc and boot file; `code-analysis.md` the layout, the libraries and the lifted/replaced boundary; `recompiler-core.md` the core as it stands here (its history is in Toy Commander's copy); `prior-art.md`; `naming.md`.

## Build and check

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DQILIN_WERROR=ON
cmake --build build --parallel
ctest --test-dir build --output-on-failure
python3 tools/check/verify_decoder.py --qilin build/qilin     # pip install capstone; 0 unexplained differences
build/qilin disc path/to/game.cue
build/qilin extract path/to/game.cue --out extracted          # outside the repo, or in an ignored folder
build/qilin info extracted/files/1TOYRACE.BIN                 # exit 0: the supported build
build/qilin cfg extracted/files/1TOYRACE.BIN                  # 5,118 functions (about 1 s)
build/qilin coverage extracted/files/1TOYRACE.BIN             # exit 0: 0 unknown bytes in lifted regions (the game); 2,656 elsewhere
build/qilin suspects extracted/files/1TOYRACE.BIN
build/qilin hwaccess extracted/files/1TOYRACE.BIN             # 96 functions, none in the game
build/qilin fpmode extracted/files/1TOYRACE.BIN --list        # 0 unproven FPU instructions in the game and middleware; 3 middleware joins (known, docs/code-analysis.md)
build/qilin lift extracted/files/1TOYRACE.BIN --out gen       # 3,186 lifted (all 1,018 referenced functions of the game), 2 not (they read VBR, to replace); gen/ is ignored, never commit it
cmake -S . -B build -DQILIN_GAME_BOOT=extracted/files/1TOYRACE.BIN && cmake --build build --target qilin_run
build/qilin_run path/to/game.cue                              # exit 3 with a report: what to write next
```

Before a milestone commit, all of these must hold: tests pass, warnings are clean (`QILIN_WERROR`), the decoder check has 0 unexplained differences, the generated code for the game compiles warning-free (`-Wall -Wextra -Wpedantic -Wshadow -Werror -ffp-contract=off`, include `recomp/runtime` and the output folder), and the differential test has 0 unexplained mismatches.

## Known facts worth not rediscovering

- The porting scripts (`match.py`, `datamap.py`, `port.py`, `tr_specific.py`) were written in a session's scratch folder and are not in the repo (they read both boot files). `docs/runtime.md` says what each step does; rewrite them from that if they are gone. `port.py` copies `recomp/` and translates `toycommander/src/` through the address map; `tr_specific.py` reapplies this game's own natives; `layout.cpp`, `bootfile.cpp` and `boot.cpp` are this project's and are kept.
- **The owner's dump** is on their PC in the Toy Racer project folder: a `.7z` of 376 MB beside the extracted `.cue` and 14 `.bin` tracks. Track 3 is 751 MB, nearly all empty. A cloud session can stage the `.7z` (it is under the per-file limit; track 3 is not) and extract it with `py7zr`, outside the repo.
- The boot file is `1TOYRACE.BIN`: SHA-256 `da29a065f9db779f0c95d778de36c019848b211ad93a667244bf58e9a10ee5d4`, 972,324 bytes, loaded at `0x8C010000`, ending at `0x8C0FD624`, entered at its first byte. No header, sections or symbols.
- The entry code sets the cache control register and jumps to `0x8C0C5440` (Shinobi's start-up), which calls the game's `main` at `0x8C0204E4`. The layout is in `recomp/src/layout.cpp`, its evidence in `docs/code-analysis.md`: game `0x8C010080`–`0x8C04CA58` (lifted, 0 unknown bytes: keep it so); middleware `0x8C04CA58`–`0x8C0A5B02` (engine, audio manager, Kamui 2, `kmdk`, the network libraries, C runtime, interleaved); data `0x8C0A5B02`–`0x8C0C5440`; Shinobi and Sega's modem library `0x8C0C5440`–`0x8C0F9BB4`, with no data blocks inside; their data to the end.
- The game never touches hardware (`qilin hwaccess`). It calls Shinobi and the modem library directly from 29 sites. One middleware module calls back into the game: the authentication module at `0x8C057B82`–`0x8C0589F6` calls four functions at the game's start (`0x8C010930`…`0x8C010B82`). It is online-mode code, which the port never reaches, and doesn't move the boundary.
- **The game recognises devices by product name**: it compares the Maple device information's name with "Dreamcast Controller" and "Racing Controller" (`0x8C0A64A0`, `0x8C0A64B8`) and takes no input from anything else. The engine keeps a 48-byte record per port at `0x8C1A413C` (buttons, presses, releases; `+40` bit 31: no device), filled each frame by `0x8C0738BA`.
- **The disc holds two programs.** The game is 16 files; the other 97 are Sega's web browser (`2_DP.BIN`, the `DP*` folders, two loaders). The browser is out of scope: never recompiled, never read.
- **No movies**, unlike Toy Commander: no AVI files, no TrueMotion player in the boot file.
- **Libraries in the boot file:** Shinobi 1.71, Kamui 2 (16,5,4,1) with `kmdk`, the audio manager ("Audio64 Ver 11", `am*`/`ac*`/`a64*`, loads `AUDIO64.DRV`, ARM code), Sega's modem library, Sega's provider-settings libraries (`ntInf`, `ntUtl`, `ntIniMdm`, `IspInfo`), NexGen's TCP/IP stack (PPP, PPPoE, modem and LAN drivers), No Cliché's engine. No Windows CE. Toy Commander's are older versions of the first three; the engine is shared (`loadscene.c`, `ressGhq.c`, `tabtree.c` are in both).
- Function discovery's rules are in `docs/recompiler-core.md`. What this game added, each because the game's coverage gate failed:
  - A data word can hold a code address by coincidence (here `0x8C024820`, the middle of the game function `0x8C02477C`, in a table at `0x8C0B9D70`). The guess is thrown out when a function with a compiled prologue contains it and nothing else supports it (`Analysis::find_evictions`), and the analysis runs again.
  - A function too long for `bra` branches inside itself with `mov.l label,rN ; jmp @rN`. A `jmp` to a constant address the function's other paths reach too is a branch (`computed_branches`), not a tail call. Two middleware functions do it, 22 times (`0x8C052528`, 7 KB of unoptimised code, and `0x8C09C09A`).
  - `bra` to itself is the code's fatal-error stop (three places, one in the game at `0x8C01832A`): lifted as `rt::hang`, never as an empty loop (which a C++ compiler may delete).
- Everything Toy Commander's `CLAUDE.md` records about the core still holds: literal pools contain dead entries that decode; pointer candidates are tried in address order; SHC tail-calls with `bra` and `bt`/`bf`; float constants are read through `mova` + `fmov @r0`; the layout's data regions must still be scanned for function pointers; unreferenced functions aren't lifted by default (710 here).
- **Toy Commander's functions are found here by matching code** (`docs/runtime.md`): hash each function's instruction words with PC-relative and branch displacements masked; a hash unique in both boot files pairs two functions (1,322 pairs), and paired functions' literal pools pair data addresses (2,131). Every native that came from Toy Commander was moved through that map. Do the same for whatever Toy Commander writes next: don't re-derive it. The scripts need both boot files and stay outside the repo (Toy Commander's dump is in the owner's Toy Commander project folder; its track 15 and track 3 are under the staging limit, and the other tracks can be empty files of the right size to extract `1GUTH.BIN`).
- Interrupts are Toy Commander's design (`interrupts.*`, `guest.hpp`: a pending flag tested at loops' backward branches). To find where a run waits, `QILIN_TIMEOUT=<seconds>`, or attach `gdb -p` and read the backtrace: the frames are `fn_<address>`.
- Shinobi here is 1.71 and differs from Toy Commander's 1.61 in places: its objects are in another order (never carry a region across by offset: match functions), the peripherals' set-up goes on to an extension check that looks for the modem (`0x8C0D0DC0`, native: nothing there), and `0x8C0D0DA6`–`0x8C0D117E` is that check's code, not Maple's.
- `main` calls the C runtime's initialisation lists (`0x8C0C54DA`); their entries are the modem library's static constructors (answered with nothing: no modem, no online mode). Toy Commander has no such list.
- Some of Shinobi is linked among the middleware here (the timer set-up `0x8C04D758`, the cable query `0x8C04DB04`), so it is lifted unless `layout.cpp` lists it as replaced.
- `0x8C04DE3C`/`0x8C04DE48` are the compiler's structure copy (a table jump into an unrolled run; replaced natively). `0x8C075CB0`, with a table at `0x8C075CF6`, looks like another such helper: expect a stop there.
- `0x003B` is not in the decoder's set but real code calls a stub that starts with it (`0x8C0A1DD4`): the development system's debugger hooks, to be replaced natively.
- The lifter: a delay slot's branch reads its condition, target and PR before the slot runs; every call checks `c.ret` against the address after its slot; `trapa` never reaches it. Every label target must be an emitted instruction, not a slot. Tests that break `div1`'s Q update, a generated switch case or the far branch must fail: keep the end-to-end tests able to catch that.
- The lifter's FPU: the current bank in `float` locals, the back bank in `c.xf`; DRn = FRn (high) : FRn+1; a 64-bit fmov puts FRn at the lower address. Denormals are flushed by the host's mode (`rt::host_fp_setup()`: FTZ+DAZ, ARM64 FZ), which every thread running lifted code must call; generated code needs `-ffp-contract=off`. NaN bit patterns from arithmetic are the host's, and FPSCR's cause/flag bits read as 0.
- The FPU: the default mode is `0x00040000` (round to nearest, **DN = 1: denormals flushed to zero**, single, 32-bit transfers, bank 0). The game never leaves it. FR is handled by swapping two bank arrays on `frchg`; the engine runs in bank 1 after some matrix-library calls (the library is around `0x8C06E2FC`–`0x8C06EC8C`). Toy Commander's open point about a dispatcher with SZ = 1 doesn't arise here.
- `0x8C05E108` clears memory through the store queues (r4 address, r5 count), called from 103 places in the game: a native replacement is needed early in bring-up. `0x8C05E01C` beside it is the same kind of routine.
- The call idiom assumption (calls preserve r8–r15) is only the compiler's convention: see the note in `cfg.hpp` before the lifter devirtualises anything.
- The dump is Redump-style: `.cue` plus 14 `.bin` tracks. Tracks 1–2 single density; track 3 (sector 45000) holds the bootstrap and directories; tracks 4–13 are the music (CD audio, ten tracks); track 14 (index 1 at 536967) holds all 113 files. ISO sector numbers are absolute disc sectors.
- SH-4 points that shape the lifter, and the approximate FPU instructions (`fmac`, `fsca`, `fsrra`, `fipr`, `ftrv`, defined in `guest.hpp`, measured with `qilin_dcref` against Flycast for Toy Commander): as in Toy Commander's `CLAUDE.md`; nothing differs here.
- Capstone 5's SH-4 mode also decodes SH-2A/SH-4A instructions and lacks `fipr`, `fcnvds`, `fcnvsd`: both are reviewed differences in `verify_decoder.py`.
- The decoder's table throws at start-up if a form leaves a bit undefined or two forms share a word: after editing `kRows`, run the tests; the pinned counts (59,001 valid words, 8,770 delayed branches) change only if the instruction set does.
- In a session's container: SDL3 won't build its Wayland support with Ubuntu 24.04's headers under the zig toolchain, so configure with `-DSDL_WAYLAND=OFF -DCMAKE_C_COMPILER=<zig cc wrapper>`; `apt-get install mesa-vulkan-drivers` gives a Vulkan 1.3 device (llvmpipe) for `QILIN_HEADLESS=1` runs and the render test. CI builds SDL3 with GCC, as Punch-Out's does.
- Building where there is no GCC 14 or Clang 19 (a session's Linux container, a Windows PC without LLVM): `pip install ziglang`, then use `python -m ziglang c++` as the compiler (a wrapper script for CMake's `CMAKE_CXX_COMPILER`). GCC 14 and MSVC are then checked only by CI: check CI after pushing. Compiler messages are annotations on the commit (`.github/matchers/compilers.json`).
- GCC's `-Wshadow` also flags a local reusing a file-scope name (Clang's and MSVC's don't), and MSVC's `[[maybe_unused]]` covers only a declaration's first declarator: both bit the sister projects.
- **Keep the two Toy projects in step.** The three rules above are general and should go into Toy Commander's core too; what either runtime learns about Shinobi, Kamui 2, the audio manager and the engine applies to both.

## Status (v0.2.0)

- The whole recompiler core runs on this game (v0.1.0): 5,118 functions now, 33 switch tables; the game region has 0 unknown bytes; every FPU instruction of the game and middleware has a proven mode. The lifter lifts 2,756 functions: all 1,018 referenced ones of the game and all but 2 of the middleware's that aren't replaced by name. The differential test: 0 mismatches.
- The runtime's bring-up (v0.2.0 and after), on Toy Commander's runtime: `qilin_run` runs the lifted game from the start-up through the middleware's system initialisation (Kamui 2's, gdFs's over the boot ROM's GD-ROM calls on the disc dump, the clock, the peripherals' set-up) and the graphics start-up (DMA, texture loads, the tile accelerator's decoder, the display's timing, interrupts), through the sound driver's installation (Toy Commander's `aica.*` and `threads.*`), through the CD audio set-up and the keyboard library's, into the game's own main loop in the menu (`trmenu.c`, `0x8C03871C`), drawn by the Vulkan 1.3 renderer in an SDL3 window and played with a controller: through the title and menus into a race, which drives. What is missing: sound output (the voices aren't mixed), the memory card, more pads and the Racing Controller, and the renderer's shadows, fog and translucent sorting. gdFs, gdd, pd, pdKbd, bu and the Maple driver are lifted regions inside Shinobi (`layout.cpp`). 5,118 functions, 3,186 lifted.
- **Shared runtime pieces live in Toy Commander's repo, and nothing waits** (the owner, 2026-11-21: "i'd rather it didnt wait"). When this game needs a shared piece that Toy Commander hasn't written (as with the GD-ROM's sub-channel command 34), write it in the Toy Commander repo (pull first: its own session is active; build, test, run its `qilin_run`, push), then move it here with the porting scripts. Never write a second copy here: this project once wrote the DMA controller, interrupts and tile accelerator input itself while that session was writing the same, and its versions were dropped.
- CI: check it after each push (six jobs). It doesn't build `qilin_run` (no game files there): build that locally with warnings as errors before pushing.
