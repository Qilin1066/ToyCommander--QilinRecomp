# Toy Commander — Recomp Roadmap & Design Targets

The requirements and scope are those of the sister projects (GBTGhoulies--QilinRecomp, ApbArcade--QilinRecomp, RhythmHeavenFever--QilinRecomp (Beat the Beat), PunchOutWii--QilinRecomp), applied to the Dreamcast.

**Guiding principle: efficiency and reliability come first.** Every design choice is judged on whether it makes the game cheaper to run on low-end hardware and whether it fails loudly and predictably instead of silently misbehaving.

## Targets
- **Game:** Toy Commander (No Cliché / Sega, Dreamcast, 1999), the USA release: product `MK-57020`, version `V1.022`, dated 1999-09-30 (`disc-analysis.md`). Other releases come after this one plays.
- **Platforms:** 64-bit Windows, Linux and macOS (Intel and Apple Silicon), on x86-64 or ARM64, with Vulkan. See *Hardware scope* below.
- **Language:** **C++23** throughout (recompiler, generated code and runtime). Minimum compilers: GCC 14, Clang 19, Xcode 16, Visual Studio 2022 17.10.
- **Graphics API:** **Vulkan 1.3, and only Vulkan.** We require the 1.3 core API, and only the optional features and limits that Mesa's v3dv driver on a Pi 4 provides, so one render path works everywhere (MoltenVK on macOS). See *Vulkan baseline* below.
- **Reference:** the original game on a Dreamcast, or in an emulator used as a black box, is ground truth for behaviour and visuals. No emulator's code, tables or measured internals go into this project (most are GPL, and a number read out of one is that emulator's code).
- **Enhancement example target:** 3440×1440 (21:9) at 144 Hz.

## Architecture
- **Game code:** static recompilation, SH-4 → **generated C++**, compiled ahead of time by GCC, Clang or MSVC for each target. No interpreter, no JIT, no emulator at run time, not even as a fallback. Hand-written C++ replaces lifted functions over time (hot paths, bugs, enhancement hooks) through a function override table.
- **Decoder:** our own, table-driven, over the SH-4's whole 16-bit encoding space, **checked word by word against Capstone** in CI (v0.1.0: `recompiler-core.md`). Anything that isn't an SH7750-family instruction is invalid.
- **Fail loudly:** an undecodable or unsupported instruction in code is a build error, never a comment; an unknown indirect-call target at run time traps with its address logged.
- **Control flow:** recursive-descent function discovery from the entry point, with resolved jump tables (SHC's `braf`/`jmp` switch forms) and literal pools told apart from code. Every byte of the boot file is to be accounted for: code, literal pool, jump table, data, padding or unknown, and unknown must reach zero in lifted code (`qilin coverage`, as in the sister projects). Indirect calls dispatch through a generated sorted function table.
- **Delay slots:** a delayed branch's slot instruction is lifted ahead of the transfer, with the branch's own operands read first where the slot changes them. A branch target that lands in a delay slot, or a slot instruction that is itself a branch, is a build error until analysis shows it happens.
- **Register model:** guest registers held in host locals inside each lifted function and synced to a context struct only at call and indirect boundaries. The T bit is a local `bool`; S, Q and M exist only where `div1` and `mac` read them. The banked registers and SR's privileged bits belong to interrupt and exception code, which is replaced, not lifted.
- **Floating point:** single-precision SH-4 arithmetic → native `float`, double → native `double`, no contraction and no fast-math, so results are the same bits on every host. What an FPU instruction means depends on FPSCR's PR, SZ and FR bits at that moment: the mode at every instruction is worked out by dataflow over each function (`fschg`, `frchg`, loads of FPSCR), and code whose mode can't be proven reads FPSCR at run time (exact, only slower), with every such place reported by `qilin fpmode`: nothing is guessed (v0.4.0: there are none in the game). The bank (FR) is handled by keeping the two banks as two arrays that `frchg` swaps, as the hardware does, so it never needs to be known. Denormals are flushed to zero, as the default mode (DN = 1) does on the hardware. The approximate instructions (`fmac`, `fsca`, `fsrra`, `fipr`, `ftrv`), whose exact results on the hardware aren't documented, have definitions of our own, chosen by measuring them against a Dreamcast emulator run as a black box (v0.7.0, the owner's call with no console at hand; `recompiler-core.md`): all agree with it except `fsca`, whose table the emulator has of its own, within 2⁻²³.
- **Memory:** flat. The Dreamcast's 16 MB of RAM appears at several aliases (the game is linked for `0x8C000000`, the uncached view is `0xAC000000`, the physical address `0x0C000000`): guest RAM is one shared-memory object mapped at each alias the game uses, inside one 4 GB host reservation (`base + addr`, no bounds checks in the release build; a checked build stops on anything else, with the address and the instruction). Both sides are little-endian.
- **Hardware boundary:** the game has no operating system under it. Sega's libraries are linked into the boot file and drive the hardware registers and the boot ROM's system calls directly. They are **replaced natively at their API**, not recompiled, where they touch hardware: the Shinobi library's system parts (interrupts, timers, cache, memory-card and controller access through Maple, the GD-ROM file system, flash settings) and the audio manager above the sound driver. Libraries that are pure computation over those (the C runtime, maths, the game's own engine and its script interpreter) are **lifted** with the game, for exact behaviour. The boundary is drawn library by library in `code-analysis.md` once function discovery has named them (step 1), and can move as the runtime is written, as it did in the sister projects.
- **Graphics:** Kamui 2 is lifted, and the port provides the hardware under it: the PowerVR2's registers, video memory, and the tile accelerator's parameter stream (global parameters, vertex types, end-of-list), decoded into Vulkan draws; an unknown parameter is fatal. Decided in the bring-up (`runtime.md`): without symbols, Kamui 2's functions can't be told apart reliably inside the interleaved middleware, and the parameter stream is the narrow, documented interface. Only what Kamui 2 actually uses is provided, and nothing beneath it is timed to the cycle: the registers behave as the code reading them needs. The PowerVR2's per-pixel translucent sorting is part of the look: the renderer has to reproduce its result within the Vulkan baseline (how is decided at step 4, with the game's actual list usage in hand). Shaders are compiled to SPIR-V offline and committed; pipelines come from a prebuilt cache (no run-time compile stutter).
- **Video:** the six movies are AVI files in Duck TrueMotion 2X with Duck ADPCM sound. The decoder is in the boot file: it is lifted with the game and its frames uploaded as Vulkan textures.
- **Audio:** the sound driver (`AUDIO64.DRV`) is ARM code for the sound chip's own CPU and is not run. The audio manager's API is replaced over a native mixer for the AICA's voices (16-bit and 8-bit PCM, Yamaha ADPCM), output on SDL3. The music is CD audio (disc tracks 4 to 14), played from the player's disc image through the GD-ROM replacement.
- **Input and saves:** controllers through SDL3 (an Xbox pad over Bluetooth is the test controller), with the keyboard on player 1; up to four players. Memory-card saves are files in the data folder; the Jump Pack becomes controller rumble.
- **Display:** the game supports the VGA box, so it runs as it does on VGA: 640×480, progressive, 60 Hz.
- **The disc:** the runtime reads the player's own dump directly (a Redump-style `.cue` with one `.bin` per track): files, the bootstrap and the audio tracks. Nothing is converted or extracted beforehand (`qilin extract` exists for analysis).
- **Threads:** audio mixing on its own thread, the GPU a submission behind the CPU, as in the sister projects.
- **Portability rules:** no inline assembly or CPU intrinsics in the runtime; ARM64 Linux builds from day one.

## Hardware scope
**Supported: 64-bit hosts with a Vulkan 1.3 driver.** In practice that means:
- **Windows and Linux** on x86-64 or ARM64 with a Vulkan-capable GPU and driver;
- **macOS on Intel and Apple Silicon Macs**, through MoltenVK (Vulkan on top of Metal): any 64-bit Mac with a Metal GPU running macOS 10.15 (Catalina) or later. The runtime (what players run) is built for macOS 10.15 and so doesn't use `std::format`, which Apple's libc++ only has from macOS 13.3; the developer tools (`qilin`, the tests) use it and need 13.3;
- **ARM boards** with Vulkan 1.3 drivers, e.g. Raspberry Pi 4 and newer (Mesa v3dv, Mesa 24.3 or later).

**Out of scope:** anything without Vulkan 1.3 (or, on Apple, a translation layer that provides it), and 32-bit hosts. Because of this there is one renderer (Vulkan) and one memory model: the Dreamcast's address space mapped flat into a 64-bit host's.

### Vulkan baseline: 1.3
The renderer targets **Vulkan 1.3** as its minimum API version: Mesa's v3dv on the Raspberry Pi 4 and 5 is 1.3 conformant from Mesa 24.3, MoltenVK supports 1.3 from v1.3.0, and current desktop drivers all ship it. The renderer is designed around what 1.3 makes core: dynamic rendering, synchronization2, extended dynamic state (fewer pipelines for the tile accelerator's per-polygon state), timeline semaphores for pacing.

1.3 core is the floor, but optional features and device limits aren't: v3dv is the reference for those. The renderer checks the features it uses at start-up and fails with a clear message if one is missing, rather than taking a fallback path. Nothing beyond 1.3 core and the v3dv feature set is used without a decision recorded here.

**Low-end reference:** a Raspberry Pi 4–class board is our reference for typical low-end hardware. It's what we measure efficiency against and test on. It is not a floor.

## Settings, not platform branches
All enhancements live behind a settings file (`toycommander.ini`) with presets, e.g.:
- *Low-end:* 1× resolution, no AF, no MSAA, original aspect and frame rate.
- *Desktop:* scaled resolution, 16× AF, MSAA, widescreen, high refresh rate.

### The settings menu
The same menu as the other recomps (Dear ImGui; Punch-Out's `punchout/src/menu.cpp` is the model, and the four are kept in step):
- **Opening:** F1 or Esc; on a controller, Back + Start. It pauses the game and saves the settings on close. **Close** and **Quit the game** sit top right.
- **Controls:** the controllers found, rumble, every button of the Dreamcast controller set by pressing it (kept in `[controls]`), back to the defaults.
- **Display:** the window (full screen with F11 or Alt+Enter, which display), the picture (whole multiples, fit, or fill the window; plain or CRT television with scanlines and phosphor stripes; smooth), vsync, frame times (F3), refresh rate (full screen at a multiple of 60 Hz, variable refresh), "look at the picture" (the menu hidden while held).
- **Game:** the enhancements (internal resolution, widescreen, and the later roadmap steps as they arrive), the graphics device, the console's own settings (language, sound mode: read the next time the game starts), sound, about.
- **Conventions around it:** the window is named after the game and opens at the largest whole multiple of 640×480 that fits; every gamepad is opened and their buttons added up; the data folder is `<per-user data>/qilin/toycommander`.

The middleware's attribution per function is done during bring-up, from where the lifted middleware stops on hardware (decision in `code-analysis.md`). To do: the asset formats the runtime must understand.
2. **Recompiler core (C++23):** 🔨 started (`recompiler-core.md`). ✅ the boot file loader, ✅ the GD-ROM reader, ✅ the SH-4 decoder (every word of the encoding space agrees with Capstone, the reviewed differences listed), ✅ unit tests without game files, ✅ CI with warnings as errors on Linux x64 (GCC 14, Clang 19), Linux ARM64, macOS ARM64 and x64, Windows, ✅ function discovery, the CFG and byte coverage (v0.2.0), ✅ coverage per region with the lifted ones gated, the hardware-access profile (v0.3.0), ✅ the FPSCR mode pass, PR and scratch registers through calls (v0.4.0). ✅ the lifter's first slice: integer code, delay slots, calls, tail calls, switches, the PR idioms and the function table, with end-to-end tests that run lifted synthetic programs under every CI compiler (v0.5.0); ✅ the FPU slice: single and double precision, 64-bit transfers, both banks, denormals flushed by the host's mode (v0.6.0); ✅ the approximate FPU instructions, measured against a Dreamcast emulator, and the last control-flow corners (v0.7.0): 2,916 of the 2,937 referenced functions outside Shinobi are lifted, every one of the game's; the 21 left have privileged instructions and are to be replaced. ✅ the differential test: every lifted instruction from random states against a reference interpreter of our own, 242,496 runs, 0 mismatches, in CI on every configuration (v0.8.0). To do: whole call trees.
3. **Runtime skeleton:** 🔨 started (`runtime.md`). ✅ `qilin_run` built from the player's boot file, loads it into guest RAM, runs Shinobi's start-up natively into `main`; ✅ the registry of native replacements, stopping on anything unregistered and naming it and its caller; ✅ SR modelled (v0.9.0). To do: the Shinobi system layer, the file system over the disc image.
4. **Boot to first frame:** the Vulkan 1.3 renderer, Kamui 2, a window on SDL3.
5. **Playable at original spec:** 640×480, 4:3, original frame rate, sound, music, movies, saves, four players; matches the original; tested on low-end reference hardware at every milestone. The settings menu arrives here, as in the sister projects.
6. **Resolution / AF / MSAA:** scaled render targets, HUD half-pixel fixups, render-to-texture handled per target.
7. **Widescreen 16:9 → 21:9:** Hor+ projection, a wider culling frustum, the HUD and menus re-anchored, movies pillarboxed, split-screen layouts checked one by one.
8. **High refresh rate:** investigate the game's tick model first (fixed step or variable); then pacing from the swapchain, or interpolation if the logic is tied to 60 Hz.
9. **Extras:** texture replacement packs (hash on upload), etc.
